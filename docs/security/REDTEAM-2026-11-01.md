## Findings

### F1 — Messages-only (and anyone without "Use full-screen takeovers") can post a live TAKEOVER and switch off an admin's takeover: the takeover check never sees the request body — CONFIRMED (High)
**Severity: High.** Capability bypass on the lowest *posting* preset, with the strongest effect a post can have (a takeover
covers the whole screen and pauses everything; Banner/Takeover rule in CLAUDE.md). No custom configuration needed: the
stock **Messages only** preset (`announcements.post` + `screen.control`) does it. It also lets that person silently
**pause any other takeover** (an admin's emergency notice included) in the same request, and they cannot remove their own
takeover afterwards (the own-post Undo refuses takeovers), so it stays until an editor/admin finds it.

**Files:**
- `src/server/app.js:261-264`: the global 16 kB JSON parser *skips* every `/api/announcements…` path (regex includes
  `announcements`), and `src/server/app.js:541` runs `requireAuth, csrfProtection, apiMutationLimiter, enforceRole, …`
  for `/api` **before** the routers are mounted (`:554`).
- `src/server/routes/announcements.js:28`: the 256 kB parser `router.use('/announcements', express.json(...))` lives inside
  the router, i.e. it runs **after** `enforceRole`.
- `src/shared/permissions.js:359-367` `writesTakeover(path, body)`: `if (!isObj(body)) return false;` — with
  `req.body === undefined` it answers "not a takeover", so `canDo` (`:404`) never asks for `announcements.takeover`.
- Introduced by `6dc72b9` ("Security M3: 256 kB body limit on /api/slides and /api/announcements only", 2026-10-25),
  which moved the parser for these paths behind the role check. The unit tests (`test/permissionsCaps.test.js:102,151-154`)
  call `canDo()` with a hand-made body, so they still pass; nothing tests the real middleware order.

**Reproduction (CONFIRMED on the throwaway; scripts `t_takeover.mjs`, `t_takeover2.mjs`):**
```
admin   POST /api/announcements {display:'takeover', content:{headlineEn:'ADMIN EMERGENCY: shelter in place'}}  -> 201 (live)
msgs    POST /api/announcements {display:'takeover', when:{expiresAt:null},
              content:{headlineEn:'NO SCHOOL TODAY - GO HOME'}, resolve:{action:'replace', ids:[<admin id>]}}     -> 201 takeover published
kiosk   GET /api/state: admin takeover enabled=false; live takeovers = ["NO SCHOOL TODAY - GO HOME" by T messages]
        shared pickTakeover(...) -> "NO SCHOOL TODAY - GO HOME"     (what the TV shows, full screen, slides paused)
msgs    DELETE /api/announcements/<own takeover>                                                                     -> 403 (cannot undo it)
control msgs POST /api/messages {type:'takeover'}   -> 403   (this legacy path IS parsed by the global parser, so the same rule works)
control view POST /api/announcements {display:'takeover'} -> 403 (no announcements.post at all)
```
The same 201 was returned for a Full editor whose admin turned takeovers **off** for them (`deny: announcements.takeover`)
and for Messages-only + `announcements.edit`.

**Impact:** any Messages-only login (the preset the owner hands to staff who should "just post messages"), or anyone who
steals one, can put arbitrary full-screen text on the TV indefinitely (`expiresAt: null`), knock an admin's live takeover
off the screen (`resolve.replace` sets `enabled:false` on the ids it names; `share`/`queue` also rewrite other takeovers'
`group`/timing), and cannot be stopped by their own Undo. The Post sheet hides the Takeover kind for them
(`PostSheet.jsx:54,82`), so the control looks present in the UI while the server does not hold it.

**Chain potential:** with F2 the same class extends to editing/reactivating takeovers; with any stored-XSS-free text it is
already a defacement/false-alarm vector ("evacuate", "no school") on the school's main display.

**Minimal fix:** parse the body before the role check for these paths: e.g. in `app.js` replace the skip with a
path-specific parser chain (`app.use('/api/announcements', express.json({ limit: '256kb' }))` and the same for every other
path in the skip regex) **before** `app.use('/api', requireAuth, …, enforceRole, …)`; or make `enforceRole` itself
refuse a write whose body is not parsed yet (`req.body === undefined && method !== 'DELETE'` -> 415/400) so a future
parser move fails closed. Also have `applyResolve` only touch takeovers the caller may edit (`announcements.edit`).
Add an end-to-end test through `createApp()`: Messages-only `POST /api/announcements {display:'takeover'}` -> 403.

### F2 — The takeover rule only reads the request body, never the stored post: "edit" without "takeover" can publish, switch on, re-show or copy-and-publish takeovers — CONFIRMED (Medium)
**Severity: Medium.** Independent of F1 (still open after F1 is fixed, because these bodies never mention a takeover).
Needs a person who holds `announcements.edit` but not `announcements.takeover` — a configuration the admin's per-person
switches offer on purpose ("Full editor minus takeovers", or "Messages only + Edit existing announcements"). For that
person the "Use full-screen takeovers" switch is decorative.

**Files:** `src/shared/permissions.js:359-367` (`writesTakeover` inspects `body.display` / `body.type` only; a PUT that
says `{status:'published'}` or `{enabled:true}`, and a `reactivate` with `{}`, carry neither), `:404` (the only takeover
check), `src/server/routes/announcements.js:116-135` (PUT merges any field onto a stored takeover), `:141-173`
(`/reactivate` publishes + enables), `:176-199` (`/duplicate` copies a takeover as the caller's own draft).

**Reproduction (CONFIRMED, `t_takeover.mjs`; admin made one *draft* takeover and one *paused* takeover first):**
```
fullNoTk (Full, deny announcements.takeover)       msgEdit (Messages + announcements.edit)
PUT  /api/announcements/<draft tk> {status:'published'}  -> 200 takeover published      -> 200
POST /api/announcements/<paused tk>/reactivate {}        -> 200 takeover enabled=true    -> 200
POST /api/announcements/<any tk>/duplicate               -> 201 draft (owned by caller)  -> 201
PUT  /api/announcements/<own copy> {status:'published', content:{headlineEn:'…'}} -> 200 takeover published (any text)
kiosk: all four takeovers active at once
```
(`PUT {enabled:true}` on a paused takeover behaves the same. For plain Messages-only the PUT/reactivate are 403, as they
need `announcements.edit`.)

**Impact:** a person explicitly denied takeovers can still put one on the screen with any text (copy any takeover, then
edit and publish the copy), or bring back a takeover an admin paused. Related, same class: Kiddush Levana takeover
settings (`PUT /api/kiddush-levana/settings|override`) are also gated by `announcements.edit` only (fixed text, lower risk).

**Minimal fix:** in `canDo`, treat a write to an existing post as a takeover write when the **stored** item is a takeover
(the route already loads it: check there, or pass the stored `display` to `canDo` the way the undo replay passes
`rec.before.display`): `PUT /api/announcements/:id`, `/reactivate`, and `/duplicate` (or make duplicates of a takeover
refuse `status:'published'` for people without the capability). Test: Full minus takeovers -> PUT `{status:'published'}`
on a draft takeover = 403; reactivate of a paused takeover = 403.

### F3 — Posts-as-slides crossovers: "Delete slides" permanently deletes anyone's post (Undo cannot bring it back), and "Delete announcements" re-orders/floods the slideshow without "Change the slides" — CONFIRMED (Medium)
**Severity: Medium.** Two capability boundaries the new "posts are real slides" model (2026-10-30) depends on do not hold.
Each needs a per-person configuration the admin UI offers (a capability switched off or on for one person); the stock
presets are not affected (Full holds all four capabilities, Messages-only none of the delete/slide ones).

**(a) `slides.delete` deletes posts.** `src/server/routes/announcements.js:424-433` (`DELETE /api/slides/:id` pre-handler):
when the row is an `ANNOUNCEMENT` ref row it calls `deleteById(row.announcementId)` with **no** `announcements.delete` /
own-post check (`canDo` only asked for `slides.delete`, `permissions.js:202`). Since posts-as-slides, every slide-style
post gets a ref row (`insertAt: 'start'` server-side, `announcements.js:97-109`, and the Slides page materialises rows for
all posts), so this reaches every post. The undo tracker records the *slide* delete (`src/server/undo.js:112-148`), so
Undo puts back only a dangling ref row: the post is gone for good, and History says "Deleted the Message slide".
```
fullNoAnnDel (Full, deny announcements.delete):
DELETE /api/announcements/<admin post>   -> 403   (control)
DELETE /api/slides/ann-<admin post id>   -> 200   -> the admin's post is deleted
History: "T fullNoAnnDel | Deleted slide | Deleted the Message slide"; admin Undo -> 200, post back? false, dangling ref row back? true
```
**(b) `announcements.delete` writes the rotation.** `POST /api/announcements/restore` (`announcements.js:230-259`, needs only
`announcements.delete`) splices `req.body.refs` into `slides.json`: any count, any index, attacker-chosen row ids
(`refRowFor(item, { id: r.row.id })`, no format check), and it also accepts any `item.id`, a free-text `createdAt`
(`nowIso: src.createdAt`, not validated) and an arbitrary `item.legacy` object (`:238`, stored verbatim).
```
msgDel (Messages + announcements.delete, no slides.edit):
PUT  /api/slides []                                            -> 403   (control)
POST /api/announcements/restore {item:{id:'restored-by-msgdel', createdAt:'2099-01-01T00:00:00.000Z',
      legacy:{extra:{blob:'A'*2000,…}}, …}, refs: 40 × {index:0, row:{id:'rowid-N-<b>x</b>'}}}  -> 201
slides.json: 42 rows, 40 of them the restored post, at the top; createdAt 2099 kept (sorts first in every list); legacy blob kept
```
**Impact:** (a) a person the admin explicitly barred from deleting posts deletes any post, unrecoverably, and the History
line hides what happened; (b) a person barred from changing the slideshow can make their post play 40+ times per rotation
(effectively holding the screen without `slides.edit`), pin it first in every post list with a future `createdAt`, and store
arbitrary JSON in `announcements.json` (up to the 256 kB body).

**Minimal fix:** (a) in the `DELETE /api/slides/:id` pre-handler, require `announcements.delete` (or the own-post rule) before
`deleteById`, otherwise remove only the row; record an `announcement.delete` undo for it. (b) In `/restore`, accept refs only
from the server's own undo record (or require `slides.edit` when `refs` is non-empty), cap `refs` to the original count,
generate row ids server-side (`refRowId(item.id)`), validate `createdAt` with `isoOrNull`, and drop `legacy` (or whitelist it).
