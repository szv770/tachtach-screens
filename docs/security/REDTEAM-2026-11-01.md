# TachTach-Screens — Red-team engagement (2026-11-01)

Report-only. No `src/` or real `data/` was touched. Dynamic tests ran against a throwaway copy
(`git archive HEAD`, HEAD `67dd7ce`, branch `claude/wizardly-ride-bnbtzj`, built with `vite build`) in the
scratchpad, inside an isolated network namespace (`unshare -rn`, loopback only, plus a `netguard` require that
refuses any non-loopback TCP/DNS), production-like env (`NODE_ENV=production HOST=0.0.0.0 TRUST_PROXY=1 LOCAL_TLS=0`,
`TACHTACH_DATA_DIR` = the scratch copy's own `data/`). Fake logins made through the users-store module: admin
(2-step on), Full editor, Messages only, View only, plus custom-capability people (Full minus takeovers, Messages +
edit, Full minus delete, Messages + delete, View + shabbos.edit / dailyWord.edit / menu.edit / shiurim.edit /
slides.edit), a fake 30-name roster, the live view on with a throwaway word. `127.0.0.2` stands in for a LAN device;
a loopback peer + `X-Forwarded-For`/`CF-Connecting-IP`/`CF-Ray` stands in for cloudflared. Scripts stay in the
scratchpad (listed at the end), none committed.

Baseline: `AUDIT-2026-10-19*.md`, `AUDIT-2026-10-25.md`, `REDTEAM-2026-10-26.md` (all their findings are marked
fixed; they were re-checked where this pass touched the same code, not re-reported).

Labels: **CONFIRMED** (reproduced on the running throwaway), **LIKELY** (proven from code with a concrete trace,
not run), **THEORETICAL** (plausible, not proven).

Status: in progress (findings are committed one by one as they are confirmed).

## Findings

### F1 — Messages-only (and anyone without "Use full-screen takeovers") can post a live TAKEOVER and switch off an admin's takeover: the takeover check never sees the request body — CONFIRMED (High)
**Severity: High.** Capability bypass on the lowest *posting* preset, with the strongest effect a post can have (a takeover
covers the whole screen and pauses everything; Banner/Takeover rule in CLAUDE.md). No custom configuration needed: the
stock **Messages only** preset (`announcements.post` + `screen.control`) does it. It also lets that person silently
**pause any other takeover** (an admin's emergency notice included) in the same request, and they cannot remove their own
takeover afterwards (the own-post Undo refuses takeovers), so it stays until an editor/admin finds it.

**Files:**
- `src/server/app.js:261-264`: the global 16 kB JSON parser *skips* every `/api/announcements…` path (regex includes
  `announcements`), and `src/server/app.js:541` runs `requireAuth, csrfProtection, apiMutationLimiter, enforceRole, …`
  for `/api` **before** the routers are mounted (`:554`).
- `src/server/routes/announcements.js:28`: the 256 kB parser `router.use('/announcements', express.json(...))` lives inside
  the router, i.e. it runs **after** `enforceRole`.
- `src/shared/permissions.js:359-367` `writesTakeover(path, body)`: `if (!isObj(body)) return false;` — with
  `req.body === undefined` it answers "not a takeover", so `canDo` (`:404`) never asks for `announcements.takeover`.
- Introduced by `6dc72b9` ("Security M3: 256 kB body limit on /api/slides and /api/announcements only", 2026-10-25),
  which moved the parser for these paths behind the role check. The unit tests (`test/permissionsCaps.test.js:102,151-154`)
  call `canDo()` with a hand-made body, so they still pass; nothing tests the real middleware order.

**Reproduction (CONFIRMED on the throwaway; scripts `t_takeover.mjs`, `t_takeover2.mjs`):**
```
admin   POST /api/announcements {display:'takeover', content:{headlineEn:'ADMIN EMERGENCY: shelter in place'}}  -> 201 (live)
msgs    POST /api/announcements {display:'takeover', when:{expiresAt:null},
              content:{headlineEn:'NO SCHOOL TODAY - GO HOME'}, resolve:{action:'replace', ids:[<admin id>]}}     -> 201 takeover published
kiosk   GET /api/state: admin takeover enabled=false; live takeovers = ["NO SCHOOL TODAY - GO HOME" by T messages]
        shared pickTakeover(...) -> "NO SCHOOL TODAY - GO HOME"     (what the TV shows, full screen, slides paused)
msgs    DELETE /api/announcements/<own takeover>                                                                     -> 403 (cannot undo it)
control msgs POST /api/messages {type:'takeover'}   -> 403   (this legacy path IS parsed by the global parser, so the same rule works)
control view POST /api/announcements {display:'takeover'} -> 403 (no announcements.post at all)
```
The same 201 was returned for a Full editor whose admin turned takeovers **off** for them (`deny: announcements.takeover`)
and for Messages-only + `announcements.edit`.

**Impact:** any Messages-only login (the preset the owner hands to staff who should "just post messages"), or anyone who
steals one, can put arbitrary full-screen text on the TV indefinitely (`expiresAt: null`), knock an admin's live takeover
off the screen (`resolve.replace` sets `enabled:false` on the ids it names; `share`/`queue` also rewrite other takeovers'
`group`/timing), and cannot be stopped by their own Undo. The Post sheet hides the Takeover kind for them
(`PostSheet.jsx:54,82`), so the control looks present in the UI while the server does not hold it.

**Chain potential:** with F2 the same class extends to editing/reactivating takeovers; with any stored-XSS-free text it is
already a defacement/false-alarm vector ("evacuate", "no school") on the school's main display.

**Minimal fix:** parse the body before the role check for these paths: e.g. in `app.js` replace the skip with a
path-specific parser chain (`app.use('/api/announcements', express.json({ limit: '256kb' }))` and the same for every other
path in the skip regex) **before** `app.use('/api', requireAuth, …, enforceRole, …)`; or make `enforceRole` itself
refuse a write whose body is not parsed yet (`req.body === undefined && method !== 'DELETE'` -> 415/400) so a future
parser move fails closed. Also have `applyResolve` only touch takeovers the caller may edit (`announcements.edit`).
Add an end-to-end test through `createApp()`: Messages-only `POST /api/announcements {display:'takeover'}` -> 403.

### F2 — The takeover rule only reads the request body, never the stored post: "edit" without "takeover" can publish, switch on, re-show or copy-and-publish takeovers — CONFIRMED (Medium)
**Severity: Medium.** Independent of F1 (still open after F1 is fixed, because these bodies never mention a takeover).
Needs a person who holds `announcements.edit` but not `announcements.takeover` — a configuration the admin's per-person
switches offer on purpose ("Full editor minus takeovers", or "Messages only + Edit existing announcements"). For that
person the "Use full-screen takeovers" switch is decorative.

**Files:** `src/shared/permissions.js:359-367` (`writesTakeover` inspects `body.display` / `body.type` only; a PUT that
says `{status:'published'}` or `{enabled:true}`, and a `reactivate` with `{}`, carry neither), `:404` (the only takeover
check), `src/server/routes/announcements.js:116-135` (PUT merges any field onto a stored takeover), `:141-173`
(`/reactivate` publishes + enables), `:176-199` (`/duplicate` copies a takeover as the caller's own draft).

**Reproduction (CONFIRMED, `t_takeover.mjs`; admin made one *draft* takeover and one *paused* takeover first):**
```
fullNoTk (Full, deny announcements.takeover)       msgEdit (Messages + announcements.edit)
PUT  /api/announcements/<draft tk> {status:'published'}  -> 200 takeover published      -> 200
POST /api/announcements/<paused tk>/reactivate {}        -> 200 takeover enabled=true    -> 200
POST /api/announcements/<any tk>/duplicate               -> 201 draft (owned by caller)  -> 201
PUT  /api/announcements/<own copy> {status:'published', content:{headlineEn:'…'}} -> 200 takeover published (any text)
kiosk: all four takeovers active at once
```
(`PUT {enabled:true}` on a paused takeover behaves the same. For plain Messages-only the PUT/reactivate are 403, as they
need `announcements.edit`.)

**Impact:** a person explicitly denied takeovers can still put one on the screen with any text (copy any takeover, then
edit and publish the copy), or bring back a takeover an admin paused. Related, same class: Kiddush Levana takeover
settings (`PUT /api/kiddush-levana/settings|override`) are also gated by `announcements.edit` only (fixed text, lower risk).

**Minimal fix:** in `canDo`, treat a write to an existing post as a takeover write when the **stored** item is a takeover
(the route already loads it: check there, or pass the stored `display` to `canDo` the way the undo replay passes
`rec.before.display`): `PUT /api/announcements/:id`, `/reactivate`, and `/duplicate` (or make duplicates of a takeover
refuse `status:'published'` for people without the capability). Test: Full minus takeovers -> PUT `{status:'published'}`
on a draft takeover = 403; reactivate of a paused takeover = 403.

### F3 — Posts-as-slides crossovers: "Delete slides" permanently deletes anyone's post (Undo cannot bring it back), and "Delete announcements" re-orders/floods the slideshow without "Change the slides" — CONFIRMED (Medium)
**Severity: Medium.** Two capability boundaries the new "posts are real slides" model (2026-10-30) depends on do not hold.
Each needs a per-person configuration the admin UI offers (a capability switched off or on for one person); the stock
presets are not affected (Full holds all four capabilities, Messages-only none of the delete/slide ones).

**(a) `slides.delete` deletes posts.** `src/server/routes/announcements.js:424-433` (`DELETE /api/slides/:id` pre-handler):
when the row is an `ANNOUNCEMENT` ref row it calls `deleteById(row.announcementId)` with **no** `announcements.delete` /
own-post check (`canDo` only asked for `slides.delete`, `permissions.js:202`). Since posts-as-slides, every slide-style
post gets a ref row (`insertAt: 'start'` server-side, `announcements.js:97-109`, and the Slides page materialises rows for
all posts), so this reaches every post. The undo tracker records the *slide* delete (`src/server/undo.js:112-148`), so
Undo puts back only a dangling ref row: the post is gone for good, and History says "Deleted the Message slide".
```
fullNoAnnDel (Full, deny announcements.delete):
DELETE /api/announcements/<admin post>   -> 403   (control)
DELETE /api/slides/ann-<admin post id>   -> 200   -> the admin's post is deleted
History: "T fullNoAnnDel | Deleted slide | Deleted the Message slide"; admin Undo -> 200, post back? false, dangling ref row back? true
```
**(b) `announcements.delete` writes the rotation.** `POST /api/announcements/restore` (`announcements.js:230-259`, needs only
`announcements.delete`) splices `req.body.refs` into `slides.json`: any count, any index, attacker-chosen row ids
(`refRowFor(item, { id: r.row.id })`, no format check), and it also accepts any `item.id`, a free-text `createdAt`
(`nowIso: src.createdAt`, not validated) and an arbitrary `item.legacy` object (`:238`, stored verbatim).
```
msgDel (Messages + announcements.delete, no slides.edit):
PUT  /api/slides []                                            -> 403   (control)
POST /api/announcements/restore {item:{id:'restored-by-msgdel', createdAt:'2099-01-01T00:00:00.000Z',
      legacy:{extra:{blob:'A'*2000,…}}, …}, refs: 40 × {index:0, row:{id:'rowid-N-<b>x</b>'}}}  -> 201
slides.json: 42 rows, 40 of them the restored post, at the top; createdAt 2099 kept (sorts first in every list); legacy blob kept
```
**(c) `slides.edit` silently takes any post off the TV.** The kiosk's `buildRotation` (`src/screen/lib/announcementView.js:99-115`)
marks a post "placed" even when its ref row is `enabled:false` and then never plays it. The admin UI only lets people with
`announcements.edit` switch a post off (`SlideManager.jsx:201,249`), but `PUT /api/slides` accepts the row from anyone with
`slides.edit`:
```
slidesOnly (View + slides.edit): PUT /api/announcements/<id> {enabled:false} -> 403 (control)
                                 PUT /api/slides [... {type:'ANNOUNCEMENT', announcementId:<id>, enabled:false} ...] -> 200
kiosk rotation: post gone; announcements.json still says enabled:true (the Posts list keeps showing it as "Live now")
```
**Impact:** (a) a person the admin explicitly barred from deleting posts deletes any post, unrecoverably, and the History
line hides what happened; (c) a person barred from editing posts hides any post from the TV while its author still sees
"Live now"; (b) a person barred from changing the slideshow can make their post play 40+ times per rotation
(effectively holding the screen without `slides.edit`), pin it first in every post list with a future `createdAt`, and store
arbitrary JSON in `announcements.json` (up to the 256 kB body).

**Minimal fix:** (a) in the `DELETE /api/slides/:id` pre-handler, require `announcements.delete` (or the own-post rule) before
`deleteById`, otherwise remove only the row; record an `announcement.delete` undo for it. (b) In `/restore`, accept refs only
from the server's own undo record (or require `slides.edit` when `refs` is non-empty), cap `refs` to the original count,
generate row ids server-side (`refRowId(item.id)`), validate `createdAt` with `isoOrNull`, and drop `legacy` (or whitelist it).
(c) In `PUT /api/slides`, keep the stored `enabled` of ANNOUNCEMENT rows unless the caller holds `announcements.edit` (or ignore
`enabled` on ref rows in `buildRotation` and switch posts only through the post itself).

### F4 — Screens/groups (G1): the documented premise "`applyScopeToUser` + today's `canDo` already give the reduced answer, G5 need not touch `canDo`" is false — a "Hallway only" editor keeps org-wide powers — CONFIRMED in the pure functions, latent (Low)
**Severity: Low today (nothing is wired: no `scope` is stored on anyone), High once G5 ships on this premise.** The pure
modules themselves held up (200,000 random scope/audience cases: no fail-open, no throw, no prototype pollution; see
coverage), but the plan for enforcing them does not: `docs/saas/SCREENS-GROUPS.md` "G1 status" says
"`applyScopeToUser(user, scope)` adds every org-wide capability to `overrides.deny`, so today's `effectiveCaps`/`canDo`
already give the reduced answer: G5 does not have to touch `canDo`." `canDo`'s rules are per *path*, and every scopable
capability opens org-wide paths.

**Files:** `src/shared/screens.js:559-588` (`SCOPABLE_CAPS`, `applyScopeToUser`), `src/shared/permissions.js:192-220`
(`RULES`: `screen.control` -> `/api/(screen|refresh|freeze)`, `slides.edit` -> all of `/api/slides`, `look.change` ->
look-only `PATCH /api/settings` + `/api/(fonts|logo)`, `announcements.edit` -> `/api/kiddush-levana`,
`announcements.post` -> `/api/quick-templates`), `docs/saas/SCREENS-GROUPS.md:510-524`.

**Reproduction (CONFIRMED with the real functions, `fz/scope_canDo.mjs`):** Full editor + `look.change`, scope
`{ groups: ['grp_…'] }` (one hallway group), `canDo(applyScopeToUser(user, scope), …)`:
```
true  POST   /api/freeze {mode:'blank', emergency:true}   freeze/blank EVERY screen (design 8: emergency = org-wide people only)
true  PUT    /api/slides []                               replace the whole org rotation, items outside the scope included
true  PATCH  /api/settings {theme:'dark', banner:{…}}     org-wide look (design 6.1: only their screens' overrides)

false PUT    /api/roster, DELETE /api/slides/x            (dropped capabilities: the deny list works for these)
```
**Impact (when wired):** the "editor for one group or one TV only" promise (design summary point 7, "fail closed

**Minimal fix (design):** keep `applyScopeToUser` for the org-wide capabilities, but G5 must add a scope check in
`canDo` (or in each route) for the scopable ones: org-wide paths (`/api/freeze` without a target, `/api/refresh`,
`PUT /api/slides` whole list, look `PATCH /api/settings`, `/api/fonts|logo`, `/api/kiddush-levana`, shared quick
templates) refused for any non-null scope, and item routes checked with `canRetarget`/`withinScope` against the stored
item. Correct the "G5 does not have to touch canDo" line in SCREENS-GROUPS.md and add these cases to `test/screens.test.js`.

**Severity: Medium** (information disclosure to anyone holding the live word, which is shared with parents and forwardable;
the picture part needs no cookie at all and keeps working after the live view is switched off). It also voids the premise
under which audit L7 accepted the public `/uploads` mount ("names are UUIDs, so only a leaked URL works"): the live view is

**Files:** `src/server/live.js:134-135` (`VIEWER_KEYS` passes `slides`, `dailyWords`, `dailyStories`, `shiurim` through),

`showOn` pins included), `src/shared/shiurim.js:650-661` (`forViewer` strips notes on shiurim and future guests, but keeps
`enabled:false` shiurim and the `changes` notes), `src/server/app.js:461-467` (`/uploads` static mount, no gate).

**Reproduction (CONFIRMED, `t_viewer.mjs`, `t_viewer2.mjs`, `t_uploadpub.mjs`; viewer = `tt_live` cookie via the tunnel stand-in):**
```

       WEB_PAGE "Staff sheet" enabled:false embedUrl https://docs.example.org/spreadsheets/d/PRIVATE-STAFF-SHEET/edit?usp=sharing
```

yesterday/today. Optionally gate `/uploads` like `/google-photos` (kiosk, signed-in, or viewer for files a switched-on slide
uses). Extend the "nothing else" assertion in `test/live.test.js` to these keys.

### F6 — Picture-upload decompression bomb: one 784 KB PNG costs ~15 s and ~0.9 GB; four at once push the server to 3.1 GB and stall the kiosk for 19 s (the speaker-photo sibling has the 40 MP cap, the media upload has none) — CONFIRMED (High)
**Severity: High.** Denial of service of the whole product (kiosk state, admin, live view) and a likely out-of-memory kill on
the Pi, from a few small uploads by a **Full editor** (`media.upload`; same trust level as last round's F4). Repeatable: the
only brake is the per-address mutation limiter (60/min). Protection exists in one route and not its sibling:
`speakerPhoto.js:51` passes `limitInputPixels: 40_000_000`, `upload.js` does not.

**Files:** `src/server/upload.js:47-70` `processImage`: `sharp(buffer)` with sharp's default limit (16383 x 16383 = 268 MP),
then **three full decodes** of the same buffer (`metadata()` + `stats()` at `:51-52`, the resize at `:56-59`, the blur at
`:62-66`); `:26` 50 MB cap (bytes, not pixels); `src/server/routes/api.js:812-852` (`POST /api/upload`, `media.upload`). Same
pattern, lower exposure: `src/server/google-photos.js:90-95` (album photos downloaded from the internet).
Why the kiosk stalls although the event loop is free: sharp runs on libuv's 4-thread pool, which every `fs` call
(`readJSON` for `/api/state`, static files, SSE helpers) also needs, so all file I/O queues behind the decodes.

**Reproduction (CONFIRMED on the throwaway, x64 sandbox with 4 cores, `t_bomb.mjs`; payload = a 16383 x 16383 black PNG,
784 KB on the wire):**
```
1 x POST /api/upload (Full editor)  -> 201 in 15,443 ms; server peak RSS 919 MB; kiosk /api/state worst 61 ms
4 x POST /api/upload in parallel    -> 201 x4 in 19,938 ms; server peak RSS 3,108 MB; kiosk /api/state worst 19,069 ms
```
For comparison, the bounded speaker-photo route (`POST /api/shiurim/photo`, 40 MP cap, 40/hour/person): 40 parallel
39.7 MP uploads -> RSS 670 MB, kiosk worst 5.6 s, i.e. bounded but still a noticeable hiccup (no concurrency cap there either).

**Impact:** a Pi 5 has 4-8 GB shared with the 4K kiosk Chromium; 3 GB of decoder memory from one editor's burst is enough for the
kernel OOM killer to take out Chromium or Node (the TV goes black or the server restarts), and on slower ARM cores each burst
freezes all file I/O for longer than here. A stolen Full-editor session (or a careless "upload this huge scan") is enough.

**Chain potential:** combined with F1-class role confusion it needs only `media.upload`; with the `/uploads` public mount the
re-encoded result is harmless (resized to the screen box), so the effect is purely resource exhaustion.

**Minimal fix:** `sharp(buffer, { limitInputPixels: 40_000_000 })` (same constant as `speakerPhoto.js`, ideally one shared
helper) in `processImage`, `processGif`'s preview and `google-photos.js`; decode once (`sharp(buffer).clone()` for the three
outputs, or `metadata()` first and refuse `width*height` over the cap before any pixel work); add a small concurrency gate
(one or two image jobs at a time, a queue for the rest) so file I/O for the kiosk never waits behind uploads. Test: a
20000 x 20000 PNG -> 400 within ~100 ms.

### F7 — Windows kit: the SYSTEM update task (and the LOCAL SERVICE server task) run whatever `node.exe` was first on the installing admin's PATH, with no check that only admins can write it — LIKELY (Medium)
**Severity: Medium** (local privilege escalation to SYSTEM on the Windows PC, conditional on how Node was installed; static
review, the kit has never run on Windows). It breaks the kit's own stated rule: "SYSTEM ... must not load anything a lower
account can edit" (`common.ps1:6`), "SYSTEM never runs git, npm or anything from the project folder" (`update-runner.ps1:12`).

**Files:** `deploy/windows/install.ps1:109-118` (`Get-NodeInfo`: `Get-Command node.exe` = first match on the admin's PATH),
`:298` (saved as `NodePath` in `%ProgramData%\TachTach\tachtach.json`), `deploy/windows/update-runner.ps1:47,51,98,153`
(as SYSTEM: `& $NodeExe $Helper validate …`), `deploy/windows/common.ps1:154-163` (`Get-TTNodeExe`, used by
`server-run.ps1` for the LOCAL SERVICE server). Nothing checks the owner/ACL of that file or its folder; the admin-only copy
of `update-helper.mjs` is protected, the interpreter that runs it is not.

**Trace:** if `node.exe` resolves to a user-writable location — nvm-windows (`%APPDATA%\nvm\…`; its default symlink even makes
`C:\Program Files\nodejs\node.exe` point there), Volta/fnm/scoop shims under `%LOCALAPPDATA%`/`%USERPROFILE%`, or a portable
Node in a user folder — then that Windows user (the kiosk account, a teacher's account on a shared PC, or malware in it)
replaces `node.exe`; the "TachTach Server" task restarts it as LOCAL SERVICE within a minute (repeat trigger), which can read
`data\` (password hashes, 2-step secrets, roster) and drop `data\update-request.json` (owner = LOCAL SERVICE, exactly what the
runner checks for); the next minute "TachTach Update" runs the same replaced `node.exe` **as SYSTEM**.

**Impact:** full takeover of the Windows PC and every secret in `data\` from an ordinary local account. The winget/MSI path the
installer falls back to is safe (admin-only), so the risk is limited to PCs where Node was already installed per-user, which is
common on staff PCs used for development.

**Minimal fix:** after resolving `node.exe` (install, runner, server-run), resolve symlinks/junctions to the real file and refuse
it unless the file and every parent folder are owned by Administrators/SYSTEM/TrustedInstaller and not writable by Users,
Authenticated Users or the kiosk account (`Get-Acl` check like the request-file owner check); prefer the MSI location
`%ProgramFiles%\nodejs\node.exe` when it is a real file. Document it in `docs/windows/RISKS.md`. Same check for `GitPath`
(run by NETWORK SERVICE, lower impact).

### F8 — Guest-speaker takeover needs only "Edit the shiurim": the "needs the takeover permission" check exists only in the admin UI — CONFIRMED (Medium)
**Severity: Medium.** A third route to a full-screen takeover that skips `announcements.takeover` (after F1 and F2). Needs a
person with `shiurim.edit` but without takeovers: e.g. a shiurim coordinator the admin gave only that switch (View only +
"Edit the shiurim and guest speakers"), or a Full editor with takeovers turned off. The text is the attacker's: the guest

### F10 — CI: actions are "pinned" to mutable version tags, not commit SHAs — CONFIRMED by review (Low)
