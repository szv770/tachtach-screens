# TachTach-Screens — Security re-audit #3 (2026-10-25)

Report-only. No `src/` change was made. Dynamic tests ran against a throwaway copy (`git archive HEAD` +
the current `dist/`) in a scratch dir, inside an isolated network namespace (`unshare -rn`, loopback only,
every outbound connection fails), with production-like env (`HOST=0.0.0.0`, `TRUST_PROXY=1`), fake logins
made through the users-store module (admin / Full editor / Messages only / View only), a fake 30-name
roster and the live view switched on with a throwaway word. `127.0.0.2` stands in for a device on the school
LAN; a loopback peer plus `X-Forwarded-For` / `CF-Connecting-IP` / `CF-Ray` stands in for cloudflared.
The real `data/` was never used, `setup.js` was never run. Scripts are described inline (small, cheap
reproductions); none are committed.

## Executive summary

The access-control core is solid: every earlier finding re-tested as fixed (section "Re-verified"), the
capability boundary held for every write tried, the public homepage is inert, no CSP violation showed up on
any real page, and `npm audit --omit=dev` is clean.

What makes it *feel* flaky is mostly **reliability bugs that look like security failures**: the server
process dies on a single bad network connect or a single unreadable data file, whole-list saves start
failing with "That request is too large" once the rotation grows, simultaneous saves silently revert each
other, and the per-address sign-in lock can shut the admin out for an hour because of someone else on the
school Wi-Fi. The live view also hands viewers far more than the TV shows (every student name with birthday,
drafts and scheduled posts, staff names, Google album links).

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 2 |
| Medium | 6 |
| Low | 8 |

Fix order (each is small):
1. **H1** one-line fix in `safeFetch.js` (defer the pinned `lookup` callback) + gate `/api/embed-probe` behind `slides.edit`.
2. **H2** catch async errors in middleware/routes (Express 5 or an `asyncHandler` wrapper) + a process-level `unhandledRejection` logger + `.bak` fallback in `readJSON`.
3. **M3** body limits for `/api/slides` and `/api/announcements`.
4. **M4** `updateJSON()` (read-modify-write under the per-file lock).
5. **M1** viewer state whitelist (today's birthdays only, active posts only, no staff names, no album URLs).
6. **M5** sign-in lock that one person on the shared address cannot trigger for everyone.
7. **M2**, **M6** live-word strength / global budget, SSE pools, viewer polling budget.

## High

### H1 — One failed connect in `safeFetch` crashes the whole server (View-only can do it on demand)
**Fixed in 98fb465** — pinned `lookup` callback deferred with `process.nextTick` (SSRF pin kept); regression test in `test/safeFetch.test.js` (IPv6 address, no route). `/api/embed-probe` now needs `slides.edit` (L1, `permissions.js`, `test/permissions.test.js`).
**Files:** `src/server/safeFetch.js:58` (pinned `lookup`), reached from `src/server/routes/embed-probe.js:35`
(GET, so every signed-in role incl. View-only), RSS preview/add/refresh (`src/fetchers/rss.js:55`,
`src/server/rss-scheduler.js`), Google album page + photo download (`src/fetchers/google-photos.js:93`,
`src/server/google-photos.js:80`).

The DNS-rebinding fix (audit N3) pins the socket to the vetted IP with a custom `lookup` that calls its
callback **synchronously**. When `connect()` then fails synchronously (ENETUNREACH: an IPv6 address on a Pi
with no IPv6 route, a route that just disappeared while DNS still answers, EADDRNOTAVAIL...), Node emits the
socket's `error` **before** `http.ClientRequest` has attached its socket error listener. The request promise
rejects with a stray `TypeError: Cannot read properties of null (reading 'setServername')` (which is caught),
and then the socket's own `error` event is unhandled and **the process exits with code 1**.

Proof (isolated netns, every route unreachable):
```
# standalone: safeFetch('https://feeds.example.org/rss', { resolve: () => [{address:'93.184.215.14',family:4}] })
caught normally: undefined Cannot read properties of null (reading 'setServername')
still running after the call
node:events:497  throw er; // Unhandled 'error' event
Error: connect ENETUNREACH 93.184.215.14:443          -> process exit code 1   (same with an IPv6 address)

# end to end: /etc/hosts maps v6only.test -> 2606:4700::1111 (bind-mounted inside the namespace)
GET /api/embed-probe?url=https://v6only.test/   as the View-only login  -> 502, then
server answers afterwards: ECONNREFUSED          (server process is dead)
```
A literal IP in the URL does not crash (no lookup involved); a hostname does. Realistic paths: (a) any
signed-in person, including View-only, types a hostname that only has an AAAA record into "Save & check"
(or calls the GET directly) on an IPv4-only Pi — a one-request remote kill; (b) a background RSS refresh or
Google photo sync while the network is half-down — the "random restart" the owner sees. systemd restarts
the service, so it looks like a blip plus a kiosk reconnect.

The old PoC `docs/security/poc/rebind-embed-probe.mjs` predates N3; re-run against the current code the
socket goes to the **vetted** address (rebinding is closed) — the crash above is what it exposes now.

**Fix (verified on the scratch copy: the same call then rejects normally with ENETUNREACH and the process
keeps running):**
```diff
-      lookup: (_h, _opts, cb) => (_opts && _opts.all ? cb(null, [{ address: addr.address, family: addr.family }]) : cb(null, addr.address, addr.family)),
+      lookup: (_h, _opts, cb) => process.nextTick(() => (_opts && _opts.all ? cb(null, [{ address: addr.address, family: addr.family }]) : cb(null, addr.address, addr.family))),
```
Also: make `/api/embed-probe` need `slides.edit` (it is an outbound fetch on the Pi's behalf; see L1),
and add a `test/safeFetch.test.js` case with a resolver that returns an unroutable address.

### H2 — Any error inside an async middleware or route kills the process; one bad data file = crash loop
**Fixed in 07e7602** — `src/server/asyncErrors.js` patches the Express router layer so any rejected async middleware/route goes to the error handler (500) instead of killing the process; `server.js` logs `unhandledRejection` (and exits only before the port is bound, so real startup failures still stop it) and logs then exits on `uncaughtException`; `readJSON` falls back to `<file>.bak` on corrupt JSON, `writeJSON` fsyncs before the rename, never replaces a good `.bak` with a damaged file, and now keeps a 0600 `.bak` for `users.json`/`live.json`/`auth.json` too; `setupCheck` answers 503 (no crash, setup gate unchanged, no "run setup.js" hint) when `users.json` is unreadable; the midnight countdown re-init is caught. Tests `test/crashProof.test.js`. `TACHTACH_DATA_DIR` lets tests use a scratch data folder.
**Files:** `server.js` (no `unhandledRejection`/`uncaughtException` handler), Express 4.22 (does not catch
rejected promises from handlers), `src/server/middleware.js:27` `requireAuth`, `:134` `localhostOrAuth`,
`:203` `setupCheck` (runs on **every** request and reads `users.json`), `src/server/live.js:141,147,156,157,171`,
`src/server/routes/auth.js:90,181,221,246` (`GET /login`, `GET /invite/:t`, `GET /signin/:t`, `POST /logout`),
`src/server/countdown.js:219` (midnight timer awaits `initCountdowns()` with no catch), `src/server/storage.js:58`
(`JSON.parse` throws, no fallback).

Proof (scratch copy): replace `data/live.json` with `{"truncated": ` and request `GET /live/some-word`
anonymously through the tunnel stand-in -> `ECONNRESET`, server gone. Same with `users.json` and any request
carrying a cookie. Node 22 terminates on an unhandled rejection.

Why it matters: `setupCheck` reads `users.json` on every single request (kiosk, `/stream`, static files),
so if that one file is ever unreadable — wrong owner after a copy/restore (GOTCHAS "Secrets on disk"
describes exactly that), a truncated write after a power cut (`writeJSON` never fsyncs, `users.json` and
`live.json` have no `.bak`), an SD-card read error — the server crashes on every request, systemd restarts
it, and it crashes again on the next request: admin unreachable, kiosk blank-cycling. Today the only thing
keeping most routes alive is that each one happens to have its own `try`.

**Fix:**
- Wrap every async middleware/route (`const ah = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next)`) — or move to Express 5, which forwards rejections to the error handler. Start with `requireAuth`, `localhostOrAuth`, `setupCheck`, `orViewer`, the live routes, `GET /login`, `/invite`, `/signin`, `/logout`.
- `server.js`: `process.on('unhandledRejection', (e) => console.error('[fatal?] unhandled rejection', e))` (log and keep serving); keep crashing on `uncaughtException` but log it first.
- `readJSON`: on a parse error, log loudly and fall back to `<file>.bak` if it parses; `writeJSON`: `fsync` the temp file before `rename` (and give `users.json` a private 0600 `.bak`, or keep the last good copy in memory).
- `countdown.js:219`: `.catch()` the midnight re-init and still schedule the next one.

**Files:** `src/server/live.js:94-110` (`viewerState` = whole kiosk state minus keys matching
`/token|secret|passw|apikey|api_key|webhook|vapid|private/`), `src/server/app.js:273-323` (the body),
`src/shared/roster.js:260` (`forKiosk`), `src/server/announcements-store.js:52` (`getStateExtras` returns every item).

  approved showing *birthday names*, but this is the school's complete student list with birth dates,
  for anyone holding the word (parents forward links).

### M2 — Live word can be brute-forced by a distributed guesser; custom words can be trivial
**Fixed in edb8f6e** — per-/48 pause (20 wrong in 10 min -> 2 min, short so the right word is not kept out) + global 300 wrong/hour -> 15 min pause for new viewers and a push to admins; default word is 3 of 64 words + 4 digits (~31 bits); custom words need 10+ characters and 6+ different letters with a plain error. Tests `test/live.test.js`.
**Files:** `src/server/live.js:31,38,133-137,147`.
- Per-address limit only (20 wrong per 10 min, keyed on `normalizeIp` = IPv6 /64). Verified: 25 wrong words from
  25 different `2001:db8:N::1` addresses -> 25 x 404, never 429. There is no global budget.
- Default word = 12 adjectives x 12 nouns x 9000 numbers = 1.3 M (about 20 bits). A single IPv6 /48 holds
  65,536 /64s, i.e. about 1.3 M guesses per 10-minute window -> the whole space in minutes.
- An admin may set a 4-character word; `miami` passes `validateWord` (see `test/live.test.js`).
- Side effect the other way: after 20 wrong tries from one address (a school or a mobile carrier's shared
  address), the **right** word also gets 429 for 10 min (verified), while `/live?w=` redirects regardless.

**Fix:** a global wrong-word budget (e.g. 300/hour total; past it, `/live/:word` answers 429 to everyone
for 15 min and pushes "someone is guessing the live word" to admins), key this limiter on IPv6 /48, a
longer default (three words + 4 digits, or 6 digits: ~33 bits), and a 10-character minimum for custom words.

### M3 — "That request is too large": whole-list saves hit the 16 kB body cap
**Fixed in 6dc72b9** — 256 kB parsers on `/api/slides` and `/api/announcements` only (everything else stays 16 kB). `test/bodyLimits.test.js`.
**Files:** `src/server/app.js:229-232` (16 kB default; exemption list does not include `slides` or
`announcements`), `src/server/routes/api.js:257` (`PUT /api/slides` = the whole rotation),
`src/admin/hooks/useAdminState.js:201` (`updateSlides` sends the whole list for every toggle / reorder /
duration edit), `src/server/announcements-model.js:40` (`MAX_LONG = 12000` chars for sicha/letter bodies).

Verified (admin, valid CSRF):
```
PUT /api/slides  34 slides (10,915 B) -> 200
PUT /api/slides  49 slides (18,070 B) -> 413 {"error":"That request is too large."}
POST /api/announcements letter body  6,000 Hebrew chars (12 kB) -> 201
POST /api/announcements letter body  9,000 Hebrew chars (18 kB) -> 413   (model allows 12,000)
```
Once the rotation passes roughly 45 picture slides (or fewer with PDF slides, whose `pdfPages` lists up to 30
names), every slide change in the admin fails. A long Hebrew letter that the editor allows cannot be saved.
**Fix:** give `/slides` and `/announcements` their own 256 kB parsers (same pattern as roster/chazan) and add
them to the exemption regex; add both to `test/bodyLimits.test.js`.

### M4 — Simultaneous saves silently overwrite each other (lost updates)
**Fixed in cac533b** — `updateJSON(file, fn, fallback)` + `SKIP` in `storage.js` (read-modify-write under the per-file lock); used for slides (api + announcements store/routes), custom days, schedule entries/categories, templates, google albums, fonts, RSS feeds (+ the RSS refresher). `test/updateJSON.test.js`. Not converted (whole-file replaces or startup-only): settings, users, roster, chazan (already serialised), `undoIo`, `scheduleStore`/`schedule-dates.js` bulk writes, builtin-slides, the announcements migration.
**Files:** `src/server/storage.js` (the lock covers only the write, not read-modify-write);
`src/server/routes/api.js:257,275,...` (slides, custom days, schedule entries, google albums, fonts, RSS
feeds: `readJSON` -> change -> `writeJSON` with awaits in between, no lock); `src/server/announcements-store.js:139,186`
rewrites `slides.json` under its *own* lock, which does not exclude api.js.

Verified: 10 parallel `POST /api/slides` -> all 10 answered **201**, the list grew by **1** (14 -> 15).
Real-life version: two staff saving at the same time, a post being published (which rewrites `slides.json`)
while someone reorders slides, an undo during an edit, the RSS refresher rewriting `rss-feeds.json` while an
admin edits a feed. The change "reverts by itself".
**Fix:** `export async function updateJSON(file, fn)` in `storage.js` that takes the per-file lock, reads,
applies `fn`, writes, releases — and use it for every read-modify-write (announcements-store and api.js
then share the same lock for `slides.json`). Settings, users, roster and chazan already serialise theirs.

### M5 — One person on the school's address can lock the admin out of sign-in for an hour
**Fixed in 07d619d** — address-wide ceiling 20 -> 100 failures and 1 h -> 15 min; a browser holding a valid trusted-device cookie for the typed person passes it; the 2-step screens (password already proven) are limited per person+address only; per person+address stays 8 / 15 min. `test/loginLockout.test.js`. Unknown-username attempts still count at full weight against the address (cheap to add later); the 429 text does not mention `npm run reset-admin` (that page is public).
**Files:** `src/server/routes/auth.js:18` (`IP_LIMIT` 20 failures -> 1 h), `:113,143,195,234` (wrong
password for ANY username, wrong 2-step code, a used/expired invite or sign-in link all count).
Behind the tunnel everyone at school (staff phones on Wi-Fi, students) shares one public address.
Verified: 20 failed logins for made-up usernames from one tunnel address, then the admin with the
**correct** password from the same address -> `429 Too many failed attempts` (for 1 hour).
A student can repeat this every hour. **Fix:** keep the tight per person+address limit; for the
address-wide lock, either raise it a lot (e.g. 100/h) or skip it for a browser holding a valid
trusted-device cookie (it already proved 2-step), and do not count unknown-username attempts at full weight.
Mention `npm run reset-admin` (clears counters) on the 429 page for the owner.

### M6 — Live view / SSE resource exhaustion and "screen online" spoofing
**Fixed in 05778a8** (shared WIP snapshot commit) — only `isLocalRequest()` streams join the kiosk pool (everyone else is a preview-type client, so a View-only login cannot evict the TV or fake `online`); max 4 viewer / 6 preview streams per address; viewer-only rate limits 120/min on `/api/state` and 30/min on `/stream`. `test/sseAbuse.test.js`. Not done: caching the assembled `/api/state` for 2-5 s.
**Files:** `src/server/sse.js:7-9,56` (pools 20 kiosk / 10 preview / 40 viewer, oldest evicted),
`src/server/routes/screen.js:13-14` (any non-viewer without `?preview=true` lands in the KIOSK pool),
`src/server/health.js:27`, `src/server/push.js:146` (online = kiosk pool non-empty), `src/server/app.js:273`
(`/api/state` has no GET limit).
Verified:
- a holder of the live word opened 45 `/stream`s: the 5 oldest (real viewers) were evicted; they reconnect
  every 3 s and evict someone else -> churn for everyone watching.
- the **View-only** login opened 21 `/stream`s without `?preview=true`: they occupy the 20-slot KIOSK pool
  (the oldest got evicted, so the real TV's stream would be too), and `/api/screen/status` then reports
  `online: true, clients: 20` with no TV connected — the "Screen offline" phone alert can be silenced.
- one viewer with 16 parallel loops pulled `/api/state` at **131 req/s** (no 429) while the kiosk's own
  `/api/state` latency rose to p50 128 ms on this x64 box; each call reads ~14 files and recomputes a
  21-day chazan forecast under a global lock (`chazanStore.js:60`). A Pi 5 has much less headroom.
**Fix:** only `isLocalRequest()` streams go into the kiosk pool (everything else is preview); never evict
the kiosk; cap viewer streams per address (e.g. 3); rate-limit viewer `GET /api/state` (e.g. 30/min per
address — the SPA polls every 5 s) and cache the assembled state for 2-5 s.

## Low

**Lows (fixed in 53c6366 unless noted):** L1 see H1 (98fb465). L2 live-view changes are written to the activity log (never the word). L3 `embedUrl`/`qrUrl` must be http(s) on save (invalid ones are dropped). L4 uploaded font names are letters/digits/space/dash only (server and CSS writer) and the file signature is checked. L5 `roster.json` and `chazan.json` are in `SECRET_FILES` (0600). L6 `POST /api/preview` removed. Not fixed on purpose: L7 (accepted, `/uploads` and `/google-photos` stay public by UUID), L8 (cookie/header notes, no change needed). Tests `test/securityLows.test.js`.

- **L1 — `/api/embed-probe` is open to every role** (`permissions.js` `canDo` returns true for any GET): a
  View-only login can make the Pi fetch any public URL (and, with H1, crash it). Require `slides.edit`.
- **L2 — Live view changes are not in the activity log.** `NOT_LOGGED` (`middleware.js:58`) skips `/api/system`
  and `liveAdminRouter` (`live.js:156-176`) logs nothing, so "who turned the public view on / changed the
  word / turned touch off" is invisible. Add `activity.record` lines there.
- **L3 — Web-page slide `embedUrl` / `qrUrl` are not validated on save** (`api.js` `SLIDE_FIELDS`, only
  `pick`). The kiosk CSP (`frame-src https: http:`) and `script-src 'self'` stop `javascript:`/`data:` today,
  and the iframe sandbox is `allow-scripts allow-same-origin allow-forms`. Validate http(s) with
  `normalizeWebUrl` server-side as defence in depth.
- **L4 — Uploaded font name reaches kiosk CSS** (`src/screen/design/fonts.js:40` strips only `'` and `\`; a
  newline or `}` passes; name comes from the upload form). A `fonts`-capable editor could inject CSS on the TV
  (defacement). Source-reviewed, not executed. Allow letters/digits/space/dash only. Font file bytes are not
  checked either (served `nosniff`, `ACAO: *`), harmless but cheap to sniff (`OTTO`/`\0\1\0\0`/`wOFF`/`wOF2`).
- **L5 — Student data files are not 0600.** `roster.json`, `chazan.json` (real names) and their `.bak` copies
  are created with the default umask (`dataPerms.js:12` `SECRET_FILES` lacks them). `data/` itself is 0700, so
  only matters if that ever changes. Add them to `SECRET_FILES`.
- **L6 — Dead broadcast route.** `POST /api/preview` (`api.js:707`) relays any 16 kB JSON to every screen and
  live viewer (`broadcastToAll`); nothing in the admin calls it and nothing renders it. Remove it.
- **L7 — Public static mounts.** `/uploads/*` and `/google-photos/*` (`app.js` static mounts) need no session,
  kiosk or viewer cookie; names are UUIDs, so only a leaked URL works — but a URL seen through the live view
  keeps working after the live view is switched off. Accept, or put `stateGate` in front (kiosk, session and
  viewer all pass).
- **L8 — Minor cookie/header notes.** `tt_live` is `HttpOnly; Secure (over the tunnel); SameSite=Lax`, 7 days,
  value = HMAC(word) so rotating the word kills it (verified). `Secure`/HSTS trust `X-Forwarded-Proto` from any
  peer (`live.js:150`, `app.js:202`), which a LAN client can only use against itself. Viewers also receive a
  `_csrf` cookie from `GET /api/state` (keyed to an empty session; useless for writes, which need a session).

## Re-verified (all PASS on the throwaway server)

- H2/N2 localhost gating: from a non-loopback peer with `X-Forwarded-For` / `X-Real-IP` / `Forwarded` /
  `CF-Connecting-IP: 127.0.0.1` -> 404; loopback + any proxy header -> 404; `Host: evil.example` (rebinding)
  from loopback -> 404; `Host: localhost` from LAN -> 404; real kiosk (loopback, `Host: 127.0.0.1`) -> 200.
- H1 rss-cache traversal: `..%2Fusers`, `..%252Fusers`, `%2e%2e%2fusers`, `..%5Cusers`, `x%00` -> 400.
- CSRF: admin write without token 403; with another person's token 403; with own token 200.
- Capability boundary: View-only got 403 on `PUT /slides`, `POST /preview`, `PUT /roster`, `PUT /chazan/settings`,
  `GET/PUT /system/live`, `GET /team`, `GET /system/update`, `POST /team`, `PATCH /settings`, `POST /screen/pause`;
  Messages-only 403 on `PUT /roster`, `PUT /system/live`. (Every login can still READ `/api/roster`: by design.)
- SSRF guard (RSS preview): `127.0.0.1`, `[::ffff:7f00:1]`, `2130706433`, `0x7f.1`, `169.254.169.254`,
  `[64:ff9b::7f00:1]`, `localhost` -> all refused. DNS rebinding: socket goes to the vetted address (see H1).
- Live allow-list (viewer cookie, via tunnel and LAN): only `/api/state`, `/stream`, `/api/kiddush-levana/shown`,
  `/api/rss/cache/:id` (+ album photos) open; `/screen` 404, `/api/screen/state` 404, `POST /api/screen/report` 404,
  every `/api/*` admin read 401, `/admin` -> login. Word rotation / switch-off invalidates the cookie.
- Session cookie over the tunnel: `HttpOnly; Secure; SameSite=Strict`, 30 days rolling (90-day cap).
- Homepage `GET /`: static, `default-src 'none'`, no data, no script.
- CSP in a real browser (headless Chromium via puppeteer-core, `securitypolicyviolation` listener + console +
  HTTP >= 400): `/`, `/login`, `/live`, the kiosk `/screen` for 30 s, the live viewer for 20 s, and all 25 admin
  sections as admin -> **zero CSP violations, zero page errors**; only a `/favicon.ico` 404 (cosmetic; add one).
  The sign-in page loads Google Fonts, so it falls back to system fonts when the Pi is offline (cosmetic).
- PDF: `execFile` with an argument array, fixed temp paths, numeric `-scale-to` clamp (`pdfScaleTo`), 25 MB /
  30 pages / 90 s caps — no argument injection. GIF/video are stored as uploaded with the declared type; served
  `nosniff` + `default-src 'none'`, so a disguised HTML file cannot run.
- Software update path: unchanged since the 2026-10-19 review (spot-checked units and `run-update.sh`).
- `npm audit --omit=dev`: **0 vulnerabilities**.

## Not tested / limits
- Nothing ran on a real Pi, real cloudflared or arm64; the throughput numbers are from an x64 sandbox.
- The H1 trigger was proven with an unroutable network namespace; whether a given Pi network produces a
  *synchronous* connect error (IPv6 address without a route, route flaps) depends on that network.
- Saas (`saas-admin`/`saas-server`) was out of scope this round.
