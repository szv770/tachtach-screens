# TachTach-Screens — Red-team engagement (2026-10-26)

Report-only. No `src/` or real `data/` was touched. Dynamic tests run against a throwaway copy
(`git archive HEAD`, HEAD `2646790`, branch `claude/wizardly-ride-bnbtzj`) built with `npm run build`,
in a scratch dir, inside an isolated network namespace (`unshare -rn`, loopback only, a `netguard`
require blocks any non-loopback TCP), production-like env (`HOST=0.0.0.0`, `TRUST_PROXY=1`,
`LOCAL_TLS=0`). Fake logins (admin / Full editor / Messages only / View only) made through the
users-store module, a fake 30-name roster, the live view on with a throwaway word. `127.0.0.2` stands
in for a LAN device; a loopback peer + `X-Forwarded-For`/`CF-Connecting-IP`/`CF-Ray` stands in for
cloudflared. Scripts live in the scratchpad (listed at the end), none committed.

Prior audits (`AUDIT-2026-10-19*.md`, `AUDIT-2026-10-25.md`) are treated as the baseline; their
findings are re-verified as fixed, not re-reported. This pass hunts for NEW issues, with extra focus
(owner request) on the **secret-in-response / info-disclosure** class.

Labels: **CONFIRMED** (reproduced on the running throwaway), **LIKELY** (proven from code with a
concrete trace, not run), **THEORETICAL** (plausible, not proven).

## Executive summary

The access-control core remains strong and every prior-audit fix re-verified as holding (localhost gating on the socket + Host + no-proxy-header, `trust proxy 'loopback'`, session-bound double-submit CSRF, the fail-closed capability allow-list, 256-bit hashed tokens, bcrypt, single-use links, 2-step with trusted-device, the settings deep-merge's `__proto__`/`constructor`/`prototype` block, the ownership store, the `safeFetch` SSRF guard, upload sniffing/UUID checks, the data-pack filename allow-list). No secret, hash, code, or token was found in any endpoint response, SSE payload, or admin API (the owner's "reset-code-in-the-Network-tab" class is **not** present here).

The real finds are two **High** issues plus three **Low** info-disclosure/layering gaps. Both Highs are *incomplete/absent bounds*: F1 shows the Google-Photos viewer gate shipped this morning (`1c70bd9`) is defeated by a plain `..`, re-opening the disabled-album leak it was written to close; F4 is a single un-rate-limited GET — reachable by **any** signed-in user, **including the View-only role** — that freezes the whole single-threaded server for ~17 s (repeatable = persistent DoS) because one chazan date-loop lacks the iteration cap its siblings have (and the capability model lets every GET through). The three Lows all concern the live view handing watchers slightly more than the TV shows (the admin SPA map, the school's zip/coords, unused feed caches).

## Findings

### F1 — `..` defeats the new Google-Photos viewer gate: a live viewer reads EVERY album (disabled/unused) + all manifests — CONFIRMED (High)
**Severity: High.** Incomplete fix. Re-opens the exact class the previous run reported as CONFIRMED and that commit `1c70bd9` ("live viewers can no longer read a disabled/unused Google Photos album") was meant to close. A live viewer (anyone holding the live word — shared with parents, forwardable) can read the cached photos of **every** album, including the ones an admin deliberately **disabled** or never put on a slide, plus every album manifest JSON.
**Files:** `src/server/app.js:74-84` (`googlePhotosGate`), specifically `src/server/app.js:77`
```js
const dir = decodeURIComponent(String(req.path || '/').split('/')[1] || '');
...
if (dir && (await viewerAlbumDirs()).has(dir)) return next();   // :79
```
and the static mount `app.use('/google-photos', googlePhotosGate, express.static(dataPath('google-photos'), …))` (`app.js:449` prod, `:490` dev).

**Root cause:** the gate authorises on **only the first path segment** (`split('/')[1]`), but then hands the *unchanged* `req.url` to `express.static`, which resolves `..` **relative to the google-photos root**. A single `..` after a valid, enabled album name cancels that segment, so the file `express.static` actually serves is a *sibling* directory (a disabled album) or any file sitting at the google-photos root — while the gate still saw the enabled album and called `next()`. `express.static`'s own `..` protection only refuses escaping the *root*, which this never does.

**Reproduction (CONFIRMED on the throwaway, current HEAD `1c70bd9`):** album `cfgA` is enabled and used by an enabled `GOOGLE_PHOTOS_SLIDE` (dir `album-vz2zwb`); album `cfgB` is **disabled** (dir `album-euppce`). As a live viewer (holding only the `tt_live` cookie, via the tunnel stand-in):
```
GET /google-photos/album-euppce/pB.jpg                             -> 404   (gate works for a direct disabled-album hit)
GET /google-photos/album-vz2zwb/../album-euppce/pB.jpg             -> 200  "DISABLED-ALBUM-SECRET-PHOTO"
GET /google-photos/album-vz2zwb/../album-euppce.json              -> 200  {"albumId":"album-euppce","photos":[{... sourceUrl ...}]}
GET /google-photos/album-vz2zwb/%2e%2e/album-euppce/pB.jpg         -> 200  "DISABLED-ALBUM-SECRET-PHOTO"   (encoded dots, literal slash)
```
The `/api/google-album/cfgB/photos` route (which hands out the `/google-photos/album-euppce/...` URLs) correctly 404s for the viewer — but the attacker does not need it: `extractAlbumId` is a deterministic transform of the album URL (and for `photos.app.goo.gl` links a weak `album-<base36 of a 31-bit hash>`), and in any case a viewer can list the *enabled* album's manifest and simply walk `../<otherdir>/`. File names inside an album are UUIDs, but the **manifest JSON at `<dir>.json` lists them all** (and leaks each photo's real `googleusercontent.com` `sourceUrl` and the album `configId`), and is itself readable the same way.

**Ceiling (also confirmed):** bounded to the `data/google-photos/` tree — `/google-photos/album-vz2zwb/../../users.json` and `../../ceiling-probe.txt` both 404 (express.static refuses escaping its own root), so this is NOT arbitrary file read. Anonymous (no live cookie) is still 404 (falls to `localhostOrAuth`), so it is viewer-reachable only (plus kiosk/admin, which is intended).

**Impact:** defeats the just-shipped control; every live-view holder sees photos the school chose to keep off the TV (disabled albums, unused albums) and the manifests (direct Google URLs + structure). Chain: combine with any future stray file written into `data/google-photos/` (progress dumps, temp files) for wider read.

**Minimal fix:** authorise on the **resolved** target, not the first segment. In `googlePhotosGate`, reject any request whose decoded path contains a `..`/`.` segment (and empty segments) before `next()`, or compute `path.relative(GP_DIR, path.resolve(GP_DIR, '.'+req.path))`, take its first segment, and require THAT to be in `viewerAlbumDirs()`. (express.static `{ dotfiles: 'deny' }` does not help — there is no dotfile here.) Add a `test/live.test.js` case: viewer `GET /google-photos/<enabled>/../<disabled>/x.jpg` -> 404.

> Note: the same first-segment-only pattern would bite any future viewer-gated static mount. The `/uploads` and `/fonts` mounts are not viewer-gated (public by design, L7 accepted), so `..` there is harmless (and still cannot escape their root).

### F2 — Admin SPA shell + bundle served unauthenticated via raw `dist/` paths (full private-API map to an anon attacker) — CONFIRMED (Low, layering)
**Severity: Low** (defence-in-depth / info-disclosure; no data or secret exposed). Confirms the coordinator's item (2).
**Files:** `src/server/app.js:428` `app.use(express.static(DIST_DIR, { maxAge: '7d' }))` serves the whole `dist/` tree, including `dist/src/admin/index.html` and `dist/assets/admin-*.js`, with no auth. The `/admin` route (`app.js:467`) is behind `requireAuth`, so an anon hit on `/admin` 302s to `/login`, but the identical SPA shell and its JS are one path away and answer 200.

**Reproduction (anon via the tunnel stand-in):**
```
GET /admin                  -> 302 /login
GET /src/admin/index.html   -> 200  (the admin SPA shell; CSP default-src 'self'; script-src … applied)
GET /assets/admin-DebAWwbL.js -> 200  (the admin bundle)
```
**What the bundle reveals (reviewed):** the **complete private `/api/*` surface** — `/api/team`, `/api/system/update`, `/api/security`, `/api/roster`, `/api/chazan/*`, `/api/schedule/*`, `/api/embed-probe`, `/api/account/*`, every route — i.e. a ready enumeration map for an unauthenticated attacker, plus the admin field/label strings ("password", "backup codes", "totp"). **No secret is present**: no API keys, no tokens, no VAPID *private* key (only the runtime `applicationServerKey` public reference); hard-coded URLs are placeholders (`charidy.com/miami`, `example.com`, `your-mivtzah-app.vercel.app`). The service worker (`/sw.js`, unauth, no-cache) deliberately caches **no app code** (only a "last known" offline page), so no app-code cache-poisoning vector.

**Impact:** low on its own — the data all lives behind the authed API — but it removes any obscurity and hands an attacker the full route list, and it is a layering inconsistency (the gated `/admin` vs. the open shell). Harmless SPA shells are common, but here it is the *admin* surface map.

**Minimal fix (optional, defence in depth):** don't blanket-serve `DIST_DIR`; serve only the public asset subpaths (`/assets`, `/icons`, `/splash`, `grain.png`, `manifest.webmanifest`) and route `/src/admin/index.html` through `requireAuth` like `/admin` (or move the admin shell out of the statically served root). Accept-and-document is also reasonable given no data exposure.

### F3 — Viewer `cache` passthrough re-leaks the school's zip, precise lat/lon and Chabad locationId that M1 strips from `settings` — CONFIRMED (Low, info-disclosure; owner focus)
**Severity: Low** (incomplete strip; undermines a deliberate privacy control). The M1 fix (commit `9bfdea1`) strips `settings.location.zip`, `settings.location.locationId`, `settings.zipCode`, `settings.chabadLocationId` from the live-viewer state on purpose ("no zip"). But `viewerState` passes the whole `cache` object through only `scrub()` (which removes keys matching `/(token|secret|passw|apikey|api_key|webhook|vapid|private)/i`), and the geocoded location sits in `cache.weather.location` and `cache.zmanim.locationId` — neither key is "secret-ish", so both survive.
**Files:** `src/server/live.js:133-134` (`VIEWER_KEYS` includes `cache`, unfiltered), `:181-198` (`viewerState` strips `settings` location keys but not `cache`), `:119-128` (`scrub`). Source of the data: `src/fetchers/weather.js:144` (`{ ...w, location }`, `location = { zip, lat, lon, name, country }`) and the zmanim cache (`locationId`).

**Reproduction (CONFIRMED, live viewer via tunnel stand-in; `cache.json` seeded with a real-shaped `weather.location`):**
```
viewer /api/state  settings.location   -> {"timezone":"America/New_York"}         (zip/locationId stripped — M1 OK)
viewer /api/state  settings.zipCode     -> undefined                               (stripped — M1 OK)
viewer /api/state  cache.weather.location -> {"zip":"33140","lat":25.8103,"lon":-80.1251,"name":"Miami Beach","country":"US"}   ← LEAK
viewer /api/state  cache.zmanim.locationId -> "chabad-loc-998877"                   ← LEAK
viewer /api/state  cache.mivtzah        -> {"standings":[...]}                      (apiKey/token correctly scrubbed)
```
**Impact:** anyone holding the (shareable, parent-forwarded) live word gets the school's **exact zip, lat/lon to ~11 m, and the stable Chabad location id** — more than the TV shows (the weather slide shows only the city name + temperature). Low sensitivity on its own (a school has a public address), but it defeats the owner's explicit M1 decision to withhold the zip, so the control reads as present while not holding.

**Minimal fix:** in `viewerState`, reduce `cache.weather.location` to display fields only (e.g. `{ name }`) and delete any `locationId` under `cache` (and, defensively, apply the same `['zip','locationId','lat','lon']` strip to `cache.weather.location` as to `settings.location`). Add a `test/live.test.js` assertion that no `zip`/`lat`/`lon`/`locationId` appears anywhere in the viewer state.

### F4 — `GET /api/chazan/swap-options?date=` freezes the whole server: unbounded day-loop on an attacker-chosen far-future date (event-loop DoS) — CONFIRMED (High)
**Severity: High** (persistent denial of service of the entire product — kiosk, admin, SSE, live viewers — triggered by a single, un-rate-limited GET from **any signed-in user, including the View-only role**).

> **Reachable by the lowest-trust role (CONFIRMED).** `canDo` short-circuits `if (reading) return true` for every GET *before* the `chazan.edit` rule (`permissions.js:271`), so the `chazan.edit` capability does NOT actually gate this endpoint — `GET /api/chazan/swap-options` is reachable by **View-only** and **Messages-only** too (verified: all three roles → 200). The View-only preset is documented as "Can look, but not change anything"; here it can take the whole display down. Only `embed-probe` was carved out of the blanket "reads are open" rule (`permissions.js:270`); this equally-expensive read was not.
**Files:** `src/server/routes/chazan.js:34-42` (`GET /chazan/swap-options`, validates only `isISO(date)` — a *format* check that accepts any year up to 9999), calling `src/shared/chazan.js:490-515` `swapOptions`, whose loop has **no iteration cap**:
```js
const cursor = s.cursor || iso;
if (iso < cursor) return { ... };          // only guards the PAST
for (let d = cursor; d <= iso; d = addDays(d, 1)) {   // chazan.js:496 — no `i < CAP`
  const { list } = dayTefilas(s, d, customDays);       // real work every iteration
  ...
}
```
`cursor` is ~today, so a far-future `date` makes the loop run for millions of days, each calling `dayTefilas`. The function is **pure and synchronous**, so it blocks Node's single thread — the whole server answers nothing while it runs. Two force-multipliers: the route is a **GET**, so (a) no CSRF token is needed and (b) the `apiMutationLimiter` explicitly `skip`s GET/HEAD/OPTIONS (`app.js:517`), so there is **no rate limit** on it.

**Reproduction — pure function cost (CONFIRMED, current HEAD):**
```
isISO("9999-12-31")  -> true
swapOptions(date=2030-10-26) ->    11 ms
swapOptions(date=2056-10-26) ->    75 ms
swapOptions(date=2126-10-26) ->   240 ms
swapOptions(date=9999-12-31) -> 17,148 ms   (17 s of synchronous CPU, event loop blocked)
```
**Reproduction — end to end (CONFIRMED on the throwaway):** a **Full editor** (has `chazan.edit`) sends
```
GET /api/chazan/swap-options?date=9999-12-31&tefila=Shacharis
```
and, 300 ms later, the real kiosk's loopback `GET /api/state` is issued: it is **blocked for the entire duration** (measured: the kiosk poll hit its 6 s client timeout while the loop ran; it would stall the full ~17 s). SSE heartbeats, admin requests and every live viewer freeze too, because the event loop is pinned. Firing the request in a loop keeps the display frozen indefinitely — a **persistent DoS** with no privilege beyond a content-editor login (Full editor), and nothing to clean up afterwards.

**Impact / chain:** the kiosk is the product; **any signed-in user — including a View-only login** — or anyone who steals any session, can take the TV dark and lock admins out at will, from a single GET, bypassing CSRF (GET) and the mutation limiter (skips GET). It needs no write capability and no `chazan.edit` (the `if (reading) return true` short-circuit means every role reaches it). This is the worst reachability a DoS can have short of unauthenticated.

**Minimal fix:** bound the date in the route to the forecast window before calling `swapOptions` — e.g. reject `date > addDays(today, FORECAST_DAYS)` (and `date < addDays(today, -LIMITS.historyDays)`) with a 400 — AND add a hard iteration cap to the loop in `swapOptions` (`for (let d = cursor, i = 0; d <= iso && i < LIMITS.maxSkipDays; d = addDays(d,1), i++)`, matching the cap already present at `chazan.js:464`/`:423`). Secondary, defence in depth: carve this expensive read out of the blanket "reads are open" rule the way `embed-probe` is (`permissions.js:270`) so it needs `chazan.edit`, and consider rate-limiting heavy GET computations. Tests: `swapOptions` returns promptly for a date years out; the route 400s a far date; a View-only login gets 403 if the capability carve-out is added.

### F5 — Live viewer reads cached items (and names) of RSS feeds shown on NO slide — the viewer RSS path has no "used/enabled" gate like the google-photos fix — CONFIRMED (Low, info-disclosure)
**Severity: Low.** Same *class* as the original google-photos finding (viewer sees content the TV does not), but RSS feeds are public-news content, so lower sensitivity. Worth noting because the google-photos fix added a "switched-on AND used by a switched-on slide" viewer gate (`viewerAlbumDirs`), while the RSS cache viewer path got no equivalent.
**Files:** `src/server/app.js:379-392` (`GET /api/rss/cache/:feedId` behind `kioskGate` = `orViewer(localhostOnly)`, so any live viewer passes; the only check is the id regex `^[A-Za-z0-9_-]{1,64}$`), and `src/server/live.js:192` (`viewerState` maps `rssFeeds` stripping only `url`, so a viewer gets the id + name of **every** feed, including feeds no enabled `RSS_SLIDE` references).

**Reproduction (CONFIRMED, live viewer via tunnel; a feed referenced by no slide):**
```
viewer /api/state  rssFeeds            -> [{"id":"feed-unused-001","name":"Private Unused Feed",...}]   (name of an unused feed)
viewer GET /api/rss/cache/feed-unused-001 -> 200  {"items":[{"title":"UNUSED FEED SECRET ITEM",...}]}    (its cached items)
```
**Impact:** a live-word holder can read the names and cached contents of feeds the admin added but did not put on screen. Public RSS content, so low, but it is "beyond what the TV shows", and the asymmetry with the (now-gated) google-photos path is the kind of gap that grows: if a future feature caches anything more sensitive under an id a viewer learns, this endpoint hands it over.

**Minimal fix:** gate `GET /api/rss/cache/:feedId` for viewers the way `/google-photos` is gated — only ids referenced by an enabled `RSS_SLIDE` in `slides.json` — and in `viewerState` drop feeds (and albums) that no enabled slide uses, not just their `url`. (A shared `viewerUsedFeedIds()`/`viewerAlbumDirs()` helper keeps the two paths consistent.)

## Secret-in-response / information-disclosure sweep (owner focus)

The owner's prompt: a real site leaked a reset code in the API response. Every endpoint response, SSE payload and state body was scanned (a recursive key+value scanner for `password/hash/secret/token/otpauth/vapid/apikey/bcrypt/JWT`-shaped keys and values) as each identity. Verdict per flow:

| Flow | What a response could leak | Verdict |
|---|---|---|
| `GET /api/team` (admin) | other users' hashes / TOTP secrets / session tokens / invite tokens | **Clean.** `publicUser()` returns only `id, username, name, role, preset, overrides, caps, hasPassword (bool), totpEnabled (bool), createdAt, createdBy, lastLoginAt, signedInDevices (count), pendingInvite {expiresAt}`. No hash, secret, or token. Scanner: clean (1846 B). |
| `GET /api/me` | own secrets | **Clean** (same serializer). |
| `GET /api/activity`, `GET /api/history` | staff names, snapshot contents, undo tokens | **Clean.** Rows carry name/action/detail/area only; `undo` carries a record id + state, never the snapshot. `isSecretKey` keeps secret-ish settings out of undo snapshots. |
| Invite / sign-in / 2-step enrol | the link token / TOTP secret in a response that the wrong party can read | **By design, scoped.** The invite/sign-in token is returned **once**, to the admin who created it (they must send it). `pendingInvite` to the team list is `{expiresAt}` only — no token. The TOTP enrol `secret`/QR is returned to the person enrolling (the documented L2 trade-off; enrolment is logged + pushed). `peekLink` returns the full user object in memory but callers read only `name/username/role` — not leaked to the client. Tokens are `crypto.randomBytes(32)` hex, stored as SHA-256. |
| Reset flow | a reset code in the body | **N/A / clean.** There is no numeric reset code; "reset" = an admin-issued invite link (hashed, single-use, GET-shows-a-page-POST-consumes). Nothing code-shaped is emitted. |
| `GET /api/system/info` (admin) | env vars, data paths, MACs, public IP | **Clean by design** (`systemInfo.js` explicitly excludes them; returns private-LAN IPv4, hostname, OS name, 7-char git hash, uptime, storage). |
| `GET /api/system/live` (admin) | the live-view HMAC `secret` | **Clean.** Returns `{enabled, word, touchScreen, touchLive, viewers}` — the word (admin needs it) but never `secret`. |
| `GET /api/state` as **viewer** | drafts, later posts, staff names, album/feed URLs, zip | **Mostly clean** (M1 allow-list holds for announcements/roster/chazan/albums/feeds `url`/settings-zip) **except F3** (`cache.weather.location` zip+lat/lon, `cache.zmanim.locationId`) and **F5** (unused feed names). `cache.mivtzah.apiKey/token` correctly scrubbed. |
| SSE `/stream` to **viewer** | raw unfiltered broadcasts | **Clean.** Viewers are `isPreview` clients; `broadcast()` skips them. The two events that do reach them carry no secret: `freeze-update` (`active.source` is only `'manual'`/`'schedule'`, not a name) and `screen-slide` (`followPayload` → `heldBy` from a 3-value allow-list, `slides` reduced to `{id, ms}` by `sanitizeList`). |
| Error bodies | stack traces, internal paths, `err.message` | **Clean.** Global handler returns fixed text per status (`publicErrorMessage`); network reasons are summarised (`networkReason`); no `X-Powered-By`. |
| Login / link errors | user-existence oracle | **Uniform.** "Invalid credentials" for unknown user or wrong password; link states differ (used/expired/unknown) but tokens are unguessable. |

## Attack chains

- **F1 alone** → any live-word holder (word is shared with parents, forwardable) reads every cached album the school chose to keep off the TV, plus manifests (direct `googleusercontent.com` URLs). Bounded to `data/google-photos/`; does **not** reach `users.json` (express.static root check holds).
- **F4 alone** → **any** signed-in user (a View-only login, or a stolen session of any role) freezes the kiosk + admin + all viewers at will with one GET, repeatable = persistent DoS. No write capability and no `chazan.edit` is needed — the `if (reading) return true` capability short-circuit lets every role reach it.
- **F2 + enumeration** → an unauthenticated attacker pulls the full `/api/*` map from the admin bundle, then probes it; every route still fail-closes (the sweep confirms), so this only removes obscurity — no escalation realized.
- **F3 + F5** → the live view leaks the school's exact location and the names/contents of unused feeds; together they let a watcher profile the site beyond the on-screen content. Low individually; listed as a pair because both are the same "viewer sees more than the TV" gap the M1 allow-list was meant to close.
- No chain to **admin**, to **`users.json` hashes/secrets**, to **arbitrary file write**, or to **code execution** was found; the capability allow-list, token hashing, `safeFetch`, and the data-pack/upload filename gates each held under the bypass attempts listed above.
