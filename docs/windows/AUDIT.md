# Windows audit: what assumes Linux / a Raspberry Pi

Written 2026-10-26 on branch `claude/wizardly-ride-bnbtzj`. Goal: TachTach Screens runs well on an ordinary
Windows 10/11 PC (or mini-PC) behind the TV, not only on a Pi.

**How this was checked.** Every file in `src/server/`, `src/fetchers/`, `server.js`, `setup.js`, `scripts/`
and `deploy/` was searched for shell-outs (`execFile`, `spawn`), file modes, renames, fixed Unix paths,
signals, systemd/timedatectl, `/tmp`, symlinks and path separators, then read around each hit. **Nothing
here was run on Windows** (the sandbox is Linux; PowerShell could not be installed in it). Line numbers are
as of commit `4d0ef07` (before the fixes in this branch).

Ranking: **H** = the screen would not work, or a security property would be lost. **M** = a feature breaks or
the box needs a person after some event. **L** = cosmetic, rare, or developer-only.

## D. Software update on Windows: design and threat model

Same promise as the Pi: **the web process can only ask; it can never choose what runs, and nothing it can
write is ever executed with more rights than it has.**

Accounts:
- `LOCAL SERVICE` runs the web server. It can write `C:\TachTach\data\` and nothing else of ours. It cannot
  write the code, `node_modules`, `.git`, `.env`, the updater copy, or the status file.
- `NETWORK SERVICE` runs the update worker (git pull, npm ci, vite build). It can write the code folder and
  `data\` (to back up and restore locally edited data files, as `update.sh` does), and its own work folder.
- `SYSTEM` runs only the updater copy in `%ProgramData%\TachTach\updater\` (Administrators + SYSTEM only).

Flow:
1. Admin clicks Update (password + 2-step as today) -> server writes `data\update-request.json` (unchanged code).
2. Task "TachTach Update" (SYSTEM, every minute) sees it. Checks: not a reparse point (no symlink/junction),
   owner SID is `LOCAL SERVICE` (S-1-5-19), size < 4 KB; then `node update-helper.mjs validate` (platform
   win32: single hard link, JSON, action allow-list, nonce never seen, < 10 min old). The request is deleted.
3. SYSTEM stops the server task (and any leftover node.exe whose command line is our `server.js`), starts the
   worker task, waits (max 30 min).
4. SYSTEM first copies `data\` to `%ProgramData%\TachTach\backups\data-<time>\` (keeps 10). Then the worker
   (NETWORK SERVICE) backs up locally edited tracked data files, runs `git pull --ff-only` (or
   `git reset --hard <hash>` for a rollback), `npm ci`, `npm run build`, and prints `TT_STAGE=` markers. The
   mode and rollback hash come from a job file SYSTEM writes into `%ProgramData%\TachTach\updater\job\`
   (the worker may only read it; SYSTEM never writes into a folder a lower account can write); the hash
   itself comes only from the SYSTEM-owned `previous-commit` file and is checked to be 40 hex characters on
   both sides. The data copy uses `robocopy /XJ` so a junction planted in `data\` is not followed.
5. SYSTEM starts the server, waits until `/screen` answers twice 5 s apart, kills the kiosk browser (watchdog
   relaunches it) and writes `update-status.json` **in its own folder** (`%ProgramData%\TachTach\updater\`),
   which the server reads (read-only). On failure after a code change: rollback the same way.

What a compromised web process (LOCAL SERVICE) can do: drop a request file (rate-limited by the runner too:
none within 2 min of the last run); so at worst it can make the PC update to what is on GitHub `main`, or
roll back one version. It cannot change the git remote, the branch, the commit, the scripts, `node_modules`
or `.env`, and SYSTEM never writes into `data\`.

Residual risks (in RISKS.md): whoever can push to the GitHub branch can run code as `NETWORK SERVICE` and,
after the restart, as `LOCAL SERVICE` (same as the Pi, where the pi user usually also has sudo); `NETWORK
SERVICE` is shared with some Windows services; the SYSTEM runner reads the worker's log (from a folder the
worker can write) to show its last lines, after checking it is not a link.
