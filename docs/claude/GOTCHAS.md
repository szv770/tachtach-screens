# Gotchas — real incidents, not hypotheticals

Read `CLAUDE.md` first. Every entry here is a bug that actually shipped and got fixed — check this before you re-introduce one of these, and check it first when something that used to work stops working.

## Bidi: root `direction: ltr` + Hebrew punctuation on the wrong side
The kiosk root (`Layout`, `ScreenScaler`, `Clock`) is `direction: ltr`. A Hebrew string rendered in an element WITHOUT its own `dir` takes the LTR paragraph direction, so trailing/leading neutral punctuation (`!` `?` `.` quotes, parentheses, `-`, `7:30`) hops to the wrong side ("מזל טוב!" showed `!` at the right). Rule: **every element that renders user/data text gets a dir from its content** -- use `<Bidi text=...>` / `bidiNodes()` (`src/screen/design/ui.jsx`, built on `src/shared/bidi.js`: `textDir`, `bidiRuns`); `Fit` does it automatically for string children. Mixed Hebrew+English strings are split into isolated `<bdi dir>` runs. Don't rely on `.tt-he` for fields that may hold English. Regression check: `node scripts/bidi-audit.mjs --base http://127.0.0.1:3000 [--seed --secs 90]` measures where the punctuation glyph sits on `/screen`. (Takeover stage text lives in `src/screen/takeover/` and is handled there.)

## Localhost-gating breaking remote/kiosk access (happened 3 times)

- `0ed54af` — `GET /api/state` was `localhostOnly`, which broke remote admin entirely (the admin SPA runs on a phone/laptop over LAN or the Cloudflare Tunnel, not on the Pi itself). Fixed by introducing `localhostOrAuth` (kiosk OR valid session cookie).
- `ba12d89` — same bug, for `/screen` and `/stream` — broke Live Preview (the admin's iframe of `/screen` is loaded from a remote browser, not localhost).
- `b4bb370` (most recent, 2026-07-20) — `localhostOnly`/`localhostOrAuth` check `req.ip`, which is only correct if Express's `trust proxy` setting matches how the reverse proxy sets `X-Forwarded-For`. Behind the Cloudflare Tunnel, every request looked non-local until `TRUST_PROXY=1` was set. **If admin/kiosk access breaks specifically over the tunnel but works fine on local WiFi, check `TRUST_PROXY` first.**

**Rule of thumb:** any new server-side endpoint the kiosk itself needs (no login) must be `localhostOrAuth`, not `localhostOnly`, unless it is truly meant to be unreachable from a remote admin session too.

## CSRF cookie must be issued before first mutation

`app.js` deliberately runs `csrfProtection` on `GET /api/state` (not just on POST/PUT/DELETE). Removing that means the `_csrf` cookie doesn't exist until the *first failing* mutation response sets it — so the first save after opening the admin panel always 403s with "CSRF validation failed" and looks like the change silently reverted. If you see that symptom, check whether `csrfProtection` still runs on the state-fetch route.

## Session rewrite storm (fixed in `auth.js`)

Rolling the session expiry on *every* validated request rewrote `auth.json` on every single API call. On the Pi this wears the SD card; on Windows dev machines it raced the atomic-rename write, so a `readAuth()` landing mid-rename saw `ENOENT`, got the default empty session, and the request 401'd — surfacing as intermittent "Unauthorized" toasts right after loading the admin panel for no reason. Fix: only rewrite once the remaining session time has drifted by more than an hour. Don't revert to per-request rewriting.

## SSE heartbeat must be a real event

A bare SSE comment (`: keepalive\n\n`) does not fire the browser's `EventSource.onmessage`. The client used that to detect a stale connection, so comment-only heartbeats made it think the stream died every ~20s and reconnect-loop. The heartbeat in `src/server/sse.js` is a real `data:` event with `type: 'heartbeat'` — keep it that way if you touch SSE.

## Windows/OneDrive file locking

`storage.js`'s atomic write (`tmp` file + `rename()`) can throw `EPERM`/`EBUSY` on Windows, especially inside a OneDrive-synced folder (this repo's local path is under OneDrive) if something else has the file open. There's a fallback to a direct non-atomic write — don't remove it or writes will crash instead of degrading gracefully. If you're debugging a "changes don't save" issue on a Windows dev box, check for `[storage] Atomic rename failed` in the console first.

## Fetchers getting blocked by Cloudflare

`626e148` — Chabad.org's Hayom Yom/Tanya pages started getting Cloudflare-blocked for the server's plain-fetch requests. Fixed by routing those specific fetches through `browserFetch.js` (puppeteer-core) instead of a raw HTTP request. If a fetcher that used to work starts silently returning stale/empty data, check whether Chabad.org's WAF rules changed again and whether it needs the same puppeteer-based bypass — check response status/HTML shape before assuming the parser itself is wrong (the parser code is well-tested; the fetch layer is the fragile part).

**Headless Chromium under the systemd sandbox (`browserFetch.js`).** puppeteer's `The browser is already running for <userDataDir>` is misleading. It is printed whenever Chromium logs `Failed to create a ProcessSingleton`, and the real cause was `process_singleton_posix.cc: Failed to create socket directory`: Chromium makes its `SingletonSocket` under `$TMPDIR`, and `/tmp` is read-only under `ProtectSystem=strict` (reproduced with a read-only bind mount). The unit has `PrivateTmp=true`. `browserFetch.js` also falls back to `data/.puppeteer-tmp/t` when the system tmp isn't writable. That fallback path must stay short: a unix socket path is capped at 108 bytes, and past that Chromium dies with SIGTRAP. HOME/XDG dirs point at `data/.puppeteer-tmp/home` because of `ProtectHome=read-only`. Launches are serialized. On a launch failure, Chromium is re-run directly so its stderr reaches the journal. Diagnose on the Pi with `npm run test:hayom-yom`, run as the service user (not root, or `data/.puppeteer-tmp` ends up owned by root). An empty Hayom Yom parse now counts as a failure, so it can't blank the last good cached entry.

## Google Photos albums were truncated (lazy loading, 2026-10-15)

A shared-album page only embeds the first batch of photos in its initial HTML; the rest are loaded while scrolling, so a single plain GET returns a partial album no matter what `maxPhotos` is (the old hard 200 cap hid this). `src/fetchers/google-photos.js` now does the plain GET (fast path) and, when it found at least `BROWSER_THRESHOLD` (40) photos, or none, scrolls the page in headless Chromium via `withBrowserPage()` in `browserFetch.js` (same TMPDIR/HOME/profile handling and serialised launches as Hayom Yom). Each pass scrolls the document and every overflow-y element by about a viewport, collects `img` src, CSS background-image and embedded-script URLs, and stops after 3 quiet passes at the bottom, `GPHOTOS_BROWSER_TIME_MS` (90 s) or `GPHOTOS_BROWSER_MAX_PASSES` (200). Results are de-duplicated by base URL (size suffix stripped), avatars filtered, order = first appearance. Any browser failure is logged (`[google-photos] browser fallback failed ...`) and the plain result is used, never worse than before. The sync writes `progress` (`listing`/`downloading` counts, throttled) into the album manifest while `status: 'syncing'`. We do not know of a reliable item-count field in Google's embedded data, so "more than found" detection is the threshold only. Local mock test: `test/google-photos-fetch.test.js` (needs Chromium; auto-uses /opt/pw-browsers). The mock host check (`http://127.0.0.1`) is only honoured with `allowLocal` or `NODE_ENV=test`. **Diagnose on the Pi** as the service user: `npm run test:google-album -- <album-url>` (add `--browser` / `--plain`); raise `GPHOTOS_BROWSER_TIME_MS` for very large albums. Not verified against real Google (sandbox was offline): if Google changes the grid markup, the browser pass may find no more than plain.

## `public/` assets aren't served in production without an explicit route

Vite copies everything in `public/` to the `dist/` root at build time, but `app.js`'s production static-file serving only mounts specific subpaths (`/assets`, `/fonts`, `/uploads`, `/google-photos`) — there was no catch-all for the `dist/` root itself. `public/grain.png` silently 404'd in production (worked fine under `npm run dev`, where Vite's dev server serves `public/` automatically) until a general `express.static(DIST_DIR)` mount was added after the more specific ones. If you add a new file to `public/` and it works in dev but 404s in prod, this is why.

## Chromium GPU-compositor degradation over long kiosk uptime (happened twice in one day, 2026-07-21)

Two separate incidents required a manual `systemctl restart tachtach-kiosk` to recover: first a washed-out, unstyled render (missing frame/grain/gold styling, tiny mis-scaled content — confirmed via `ContextResult::kFatalFailure: CommandBufferHelper::AllocateRingBuffer() failed` spamming the kiosk journal), later a frozen display (theme and slide rotation both stuck, though the clock kept ticking — proving the browser tab itself hadn't fully frozen, just some render/data path had). No code bug was found that independently explains either failure; both are attributed to the Pi 5's GPU degrading under sustained native-4K rendering of this app's heavier effects (the SVG grain filter — since replaced with a static texture — blend modes, box shadows, the whole-canvas scale transform). Mitigation: a nightly 3:15 AM kiosk restart (`deploy/tachtach-kiosk-restart.timer`) so degradation never accumulates long enough to fail during the day. If the kiosk looks broken/frozen again despite that, check `journalctl -u tachtach-kiosk` for the same `AllocateRingBuffer` signature before assuming a new bug.

**Recurred 2026-10-15 (08:27, ~5 h after the 03:15 restart, on the new design):** TV showed stale/garbled tiles (rail weather block, bands of old content) with the journal flooded by `kFatalFailure ... AllocateRingBuffer() failed`. A fresh restart (update.sh) cleared it. The nightly restart alone is not enough, so `deploy/kiosk-launch.sh` now runs Chromium under a **GPU watchdog**: 10 `kFatalFailure` / "GPU process isn't usable" lines within 60 s kill Chromium, the script exits, and `Restart=always` brings up a clean kiosk in ~5 s (journal line: `[kiosk-launch] GPU failure flood`). Tested with a fake Chromium, not yet seen on the Pi. Diagnostics on the Pi that morning: 2 GB RAM free, `/dev/shm` empty, no OOM/CMA/v3d errors in dmesg, `throttled=0x0`, 58-60 C, no photo sync in the server log (so not Google Photos; Hayom Yom's headless browser ran at 08:21 but also ran 7 times that morning without harm). The flood started with no preceding warning exactly 5h12m after the 03:15 restart, so the restart timer now fires every 4 hours (03/07/11/15/19/23:15) to stay inside that window. If the watchdog fires often, the GPU is genuinely overloaded at native 4K: next steps are running the TV at 1080p (`xrandr`/Pi display settings) or Chromium GPU flags, tested on the Pi.

## Web page slide: Charidy only allows https parents, so the kiosk runs on local https (2026-10-18)

`curl -sI https://charidy.com/miami+` shows no `X-Frame-Options` but `Content-Security-Policy: ... frame-ancestors 'self' https:`. A scheme source `https:` matches https pages only, and the kiosk used to load from `http://127.0.0.1:3000`, so Chromium refused to frame Charidy ("Refused to frame ... an ancestor violates ... frame-ancestors"). Fix: the server also listens on `https://127.0.0.1:3443` (loopback only, `src/server/localTls.js`, self-signed cert generated once into `data/tls/` with `openssl`, `LOCAL_TLS=0` disables), and `deploy/kiosk-launch.sh` prefers it (journal: `using local https`) with `--allow-insecure-localhost`, falling back to http if it is not answering. The admin "Save & check" probe judges a site's `frame-ancestors` against that real origin (`evaluateFramePolicy(headers, parentOrigin)`), and warns that `http://` pages are blocked as mixed content on an https screen. The old http listener (LAN/admin) is unchanged. If framing a site still fails, run `curl -sI` on it and compare its `frame-ancestors` with `https://127.0.0.1:3443`.

## Nightly restart looped itself into start-limit-hit (confirmed 2026-10-14; the real cause of the 2026-10-13 incident)

The ORIGINAL `tachtach-kiosk-restart.service` had `Requisite=tachtach-kiosk.service`. systemd propagates a *restart* of a required unit to the units that require it, so `systemctl restart tachtach-kiosk` (run by that very service) restarted the restart service, which ran `systemctl restart tachtach-kiosk` again, and so on every ~5 s (the kiosk's `ExecStartPre=sleep 5`) until `StartLimitBurst=5` tripped → `Result: start-limit-hit`, kiosk dead, desktop left showing. Journal signature: kiosk "Started/Stopped" every 5 s five times, the restart service "Main process exited, code=killed, status=15/TERM", and finally "Dependency failed for tachtach-kiosk-restart.service". It happened at 03:15 on 2026-10-14 (timer) and at 16:23 on 2026-10-13 (first restart-triggering event). The earlier "Persistent=true catch-up after a clock jump" explanation below was incomplete — the clock jump only supplied the trigger. Fix (already in the units): no `Requisite=`/`Requires=`/`BindsTo=` between the restart service and the kiosk, `reset-failed` first, `StartLimitIntervalSec=0`. **Never add a dependency from the restart unit to the kiosk unit.** If the old units are still installed on a Pi (`systemctl cat tachtach-kiosk-restart.service | grep Requisite`), run `deploy/update.sh` or `sudo bash deploy/install-services.sh`.

## Wi-Fi password dialog pops up over the kiosk (2026-10-14)

Symptom (photo from the TV): a "Wi-Fi Network Authentication Required — Passwords or encryption keys are required to access the Wi-Fi network '<SSID>'" window sits on top of the fullscreen kiosk. **The Pi was online** (SSH worked, normal network fine) — the dialog was about a *second, unwanted* saved network ("Admin-Only") that NetworkManager tried to autoconnect (e.g. when the main link blipped or that AP looked stronger) and has no usable saved password for. NetworkManager asks the desktop's secret agent, which puts a window on top of the kiosk. Two possible reasons it has no password: it was saved *agent-owned* (in the user keyring, locked under desktop auto-login) or it was never saved / the router password changed.
Diagnose (read-only): `nmcli -f NAME,TYPE,AUTOCONNECT,AUTOCONNECT-PRIORITY,DEVICE connection show` and `nmcli -f IN-USE,SSID,SIGNAL,SECURITY device wifi list`.
Fix depends on intent: not wanted → `sudo nmcli connection modify "<SSID>" connection.autoconnect no` (or `connection delete`); wanted → `sudo bash deploy/wifi-system-wide.sh` (stores the PSK system-wide, `psk-flags 0`, all users); make the intended network win with `connection.autoconnect-priority 50`. Best of all: wire the Pi with Ethernet. Note: an earlier version of this entry wrongly blamed the Pi being offline and for the Pi missing updates — the old screen design on the TV was just `update.sh` not having been run yet.

## Kiosk dead after a power cut: stale clock → restart burst → start-limit-hit (2026-10-13)

The Pi 5's RTC has no battery by default, so after unplugging it boots with the last saved clock (here: weeks behind). Two things followed: (1) every HTTPS fetch at startup failed with `certificate is not yet valid`, so all data fell back to cache; (2) when NTP jumped the clock forward, the `Persistent=true` nightly kiosk-restart timer caught up on "missed" runs and restarted the kiosk 5× in ~20s, tripping `StartLimitBurst=5` → `failed (Result: start-limit-hit)`, with a blank TV until a manual restart. The restart service's `Requisite=` also meant the nightly restart couldn't recover a failed kiosk. Fixes: timer `Persistent=false`, kiosk/server `StartLimitIntervalSec=0`, restart service runs `reset-failed` first and has no `Requisite=`, server `ExecStartPre` waits (≤90s) for NTP sync (`deploy/wait-for-time-sync.sh`), kiosk launches through `deploy/kiosk-launch.sh` (waits for the display and a real `/screen` response, clears Chromium crash-restore state/locks). Same incident: puppeteer's headless Chromium failed with `The browser is already running for <userDataDir>` because `ProtectSystem=strict` left `/tmp` read-only (it needs it for its singleton socket) — fixed with `PrivateTmp=true`. Also: `update.sh`'s `git pull` had been silently aborting because the admin panel edits tracked `data/*.json` files; it now backs them up, pulls, and restores them. `update.sh` re-runs `deploy/install-services.sh` so unit changes actually reach the Pi.

## Schedule countdown alerts were dead end-to-end (fixed 2026-10-14)

Four independent bugs, each enough on its own to stop alerts: (1) `countdown.js` compared lowercase day codes (`'sun'`…`'shabbos'`) with the stored `'Sun'`…`'Shabbos'`, so nothing was ever scheduled; (2) the admin saved `alertDisplay` but the API whitelist kept only `countdownDisplay`, so "Takeover" was silently dropped; (3) the server broadcast `displayMode`/`name`/`secondsRemaining` while the kiosk read `.mode`/`.eventName`/`.targetTime`; (4) slide mode rendered only on a `COUNTDOWN` slide that nothing ever put into rotation. Now: day checks go through `src/shared/scheduleDays.js` (case-insensitive; also used by ScheduleSlide and the sidebar "starting in N min", which now honor `days`/`enabled`); the API accepts `alertDisplay` as an alias but stores `countdownDisplay`; the server sends both `displayMode` and `mode` plus `targetTime`, and `App.jsx` normalizes either shape; slide-mode countdowns take over the slide area (like a board, rotation not paused) and a running countdown is also returned by `/api/state` so a reconnecting kiosk still shows it. **Rules:** never compare day codes with `includes()` directly; use the shared helper. If you change an SSE payload, check the client reads the same field names. A quick check: `[countdown] Scheduled N alert(s) for today (Wed)` in the server log should show N > 0 when the schedule has alerts.

## Admin settings wrote keys the server never read (fixed 2026-10-14)

SettingsPanel wrote top-level `zipCode`, `chabadLocationId`, `trackA`, `trackBTime`, but the server reads only `settings.location.{zip,locationId}` and `settings.scheduler.{trackA,trackBTime}`, so changing the zip in the admin did nothing. The admin now reads/writes the nested keys. `src/server/settings-migrate.js` folds stray top-level keys into the nested ones at startup and on every `PUT /api/settings` (idempotent; the nested value wins if both exist, because that is what was actually in effect). `PUT /api/settings` still writes the whole object with no whitelist, so **any new server-read setting must be written by the admin under the exact key the server reads.** Grep both sides before adding one.

## Kiosk canvas scaling (fragile — several fixes in a row)

`bca8429` → `74be920` → `626e148` (same day) all touched how the kiosk canvas scales to fill the actual TV resolution: scale-to-fill, then pin the scaled canvas to top-left (it was drifting/centering oddly), then a UI zoom pass. This is in `ScreenScaler.jsx`. If the screen looks shifted, cropped, or offset on a real TV after a change, this is the first file to check — it's been touched more than any other single screen-side file recently.

2026-10-13: the scale used to be non-uniform (`scale(vw/1600, vh/900)`), which stretched everything on any non-16:9 viewport (desktop Preview tab ~1920x940, portrait monitors). It's now a single uniform scale = `min(vw/1600, vh/900)` with the canvas's logical width/height grown to `vw/scale` × `vh/scale`, so it fills exactly with no distortion. On a 16:9 TV this is byte-for-byte the old 1600x900 @ 2.4×. Don't reintroduce separate x/y scales. Also: measure slide fit in layout px (`clientHeight`/`scrollHeight`), not `getBoundingClientRect()` — the latter includes this transform.

`74be920` also suppressed a Google Translate prompt that was appearing over the kiosk — Chromium's built-in translate popup, not app code; suppressed via Chromium launch flags / meta tag, not a screen bug.

## Never use `setup.js` to reset credentials

`node setup.js` re-initializes `settings.json`/`slides.json`/etc. from scratch — it is meant for first-time setup only. If the admin forgets their password or loses their TOTP device, the only safe path is `npm run reset-admin` (`scripts/reset-admin-credentials.js`), which touches only the specific `auth.json` field(s) requested. `ff8f8b5` had to fix `setup.js` itself clobbering existing `slides.json` defaults on a second run — evidence this file is not idempotent and shouldn't be treated as one.

`006f6f1` — an npm audit fix pulled in a `fast-xml-parser` major version with a breaking parsing change; the zmanim RSS parser (`src/fetchers/chabad.js`) had to be guarded against it. ## Announcements: one rule source, migration in code (2026-10-14)

Messages, pinned notes and custom text slides used to have six separate expiry checks and three renderers. They are now one file (`data/announcements.json`) and one pure rule module (`src/shared/announcements.js`). **Never add an expiry/"is it showing" check anywhere else** — call `isActive`/`selectActive`. The legacy-to-announcements migration runs at server start in code (not via committed data) because `update.sh` restores the Pi's own `data/*.json`; it is idempotent (skips ids already migrated) and backs up to `data/legacy/`. `PUT /api/slides` whitelists `announcementId` — drop it and every ANNOUNCEMENT ref row in the rotation silently breaks. Also: the banner strip used to start its text at x=+100% of a very wide repeated string, so a new banner was invisible for ~25 s; it now starts at the left edge — don't reintroduce a right-edge start without accounting for the text width.

## Kiosk design system rules (Phase 4, 2026-10-14)

- **Never hard-code a colour or font in a screen component.** Use `var(--text|--dim|--accent|--raised|--ink|--inkDim|--fill|--fillInk|--accentText|--line|--past)` and the font vars (`--f-he-d --f-he --f-en-d --f-en --f-num --f-th --f-te`, helpers in `src/screen/design/ui.jsx`). Hebrew sizes go through `he(px)` (= `calc(px * var(--he-scale))`, the global `settings.hebrewFontScale`). The legacy `getTokens()`/`fonts.*` objects still exist for the admin; `fonts.*` now resolves to the CSS vars.
- **Fade past rows with a colour (`--past`), never `opacity`.** `opacity` groups produced compositing seams in the mockup pass and cost more on the Pi.
- **Outside takeovers, the only things allowed to animate are page transitions** (opacity/transform, `settings.motion`) and the banner marquee when text overflows. No infinite animations, `filter: blur`, `backdrop-filter`, `mix-blend-mode`, or the old grain overlay (it was a suspect in the GPU-degradation incidents above). **Takeovers/announcements are the one owner-approved exception** (2026-10-14, round 3b): they get an entrance plus gentle looping ambient motion, under the rules in "Takeover animation rules" below. `useSlideRotation` no longer runs a `requestAnimationFrame` progress loop (it re-rendered the whole App every frame and nothing shows progress any more).
- **Day/night crossfade** works because the 8 base roles are `@property`-registered `<color>`s and every derived role is a `color-mix()` of them; transition is 4 s on `.tt-root`. If a role is added that isn't derived from the base 8, it will flip instead of fade. Light vs dark derivation is by luminance, not by the family label.
- **`sepia` changed meaning.** It is now a light paper theme; the old dark brown is `walnut`. `migrateThemeSettings()` (src/shared/themes.js, run by `normalizeSettings` at startup and on every `PUT /api/settings`, guarded by `settings.themeVersion`) renames it once and maps `hebrewFontScale` (owner's 1.4 -> 1.1) and seeds `layout.railSide` from `clockSide`. The admin now writes both `layout.railSide` and `clockSide` (migration prefers `layout.railSide`).
- **Auto-fit uses one-shot binary searches** (`design/fit.jsx`, `design/Paged.jsx`), measured in layout px, re-run on resize/font load. Use `vcenter` when text must sit centred in its box. Don't call them per frame.
- **`ensureBuiltinSlides()`** adds the WEATHER slide row at startup because `update.sh` keeps the Pi's own `slides.json`. Any future built-in slide type must be added to `LATE_BUILTINS` in `src/server/builtin-slides.js` too (and `SlideManager` BUILT_IN_TYPES).
- **Weather**: `fetchAll()` fetches it (Tracks B/C), keeps the last good value on failure, and the geocoded zip is cached in `cache.weather.location`. The sandbox could not reach Open-Meteo; shapes are covered by fixture tests (`test/screenDesign.test.js`), so verify once on the Pi (`curl` the log for `[weather]`).
- **One-line `Fit`s used to wrap (fixed 2026-10-14).** React clears a style key passed as `undefined`; `textWrap: undefined` removed `text-wrap`, which in current Chromium is a longhand of the `white-space` shorthand, so `whiteSpace: 'nowrap'` silently became `normal`. `Fit` now only sets `textWrap` when `wrap` is on. Don't pass `textWrap`/`whiteSpace` as `undefined` next to each other in a style object.
- **Logo recolouring is a CSS mask, not a filter** (`components/Credit.jsx`): match-theme / accent paint `var(--text)` / `var(--accent)` through the logo's alpha with `mask-image` (static, follows the theme crossfade). The old `filter: brightness(0) invert(1)` / sepia filters and `--logoFilter` are gone; don't bring back `filter` or `mix-blend-mode` for the logo.
- **Learning-page cards fit in steps, not continuously** (`LimudimSlide.jsx` `TIERS`): every card shares the first tier at which all of them fit, so English never drops under the 20 px floor and Hebrew perakim stay at least as big as their English. The tier resets when the content changes and once more after `document.fonts.ready` (fallback fonts are wider and would otherwise lock a smaller tier).

## Takeover animation rules (round 3b, 2026-10-14)

The owner explicitly **relaxed the "no infinite animations" rule for takeovers and announcements only** (every style except `quiet`): they play an entrance (max 1.2 s) and slow ambient loops (flames, confetti, ripples, drifting friezes...). The rest of the screen keeps the Phase 4 rules above. Discipline that makes this safe on the Pi (all enforced by `scripts/takeover-audit.mjs`):

- **Only `transform` and `opacity` ever animate.** No `filter`, `blur`, `backdrop-filter`, `mix-blend-mode`, `box-shadow` or clip animation, in keyframes or on any element. Glows are static radial-gradient SVG whose *opacity* breathes.
- **Each moving thing is its own small layer** (`.lay > .lp` in `src/screen/takeover/art.js`); at most **10 looping layers per style** (the audit counts `document.getAnimations()`). Keep layers small: layer area x 4K is the GPU cost (see README table in `docs/design/2026-10-14-takeovers-r3/`).
- **Every loop is seamless**: alternate direction, equal first/last keyframe, opacity 0 at both ends (ripple/rise/bus), a translate of exactly one content period over duplicated content (confetti `kFall`, friezes `kDrift`), or a 360 degree spin. Never a hard jump on the loop boundary.
- **Static states must still look right.** `Animation = Entrance only / Off` and `prefers-reduced-motion` stop every loop, so loops that only make sense in motion (ripples/rings) are hidden (`opacity:0`) and rising pieces (balloons, sparks) rest half way up (`css.js` "Static states"). If you add an ambient layer whose keyframes start at opacity 0, add it to those rules or it will show full-strength when still (balloons once sat on top of the clock).
- **Per-announcement `look.animation` = `full | entrance | off`** (default `full`) x the global `settings.motion`: smooth = full, minimal = entrance only, lively = full + extras (words/digits reveal one by one, bigger overshoot). The stricter wins (`effectiveAnimation()` in `src/shared/takeoverStyles.js`). `quiet` never loops by design.
- **Measure in layout px.** The stage is scaled by `ScreenScaler` (and again when drawn inside a slide or a picker thumbnail), so `getBoundingClientRect()` lies; `fit.js` uses `offset*/client*/scroll*` and `offsetIn()`. A tile in its entrance animation is `scale(.9)` for a moment, another reason not to use rects.
- **Never fit text that has been split for the lively reveal.** `splitLively()` wraps words/digits in inline-block spans; `fitAll()` calls `unsplit()` first (the first version re-fitted after splitting and the hype number came out 17% too small).
- **Unique ids.** SVG gradient ids come from a never-resetting counter and the trip bus keyframes get a per-build name (`kBus<n>`), because a takeover can sit on top of a slide that draws another stage.
- **Entrance only on mount.** `TakeoverStage` drops the `.enter` class after 1.6 s, so editing text in the admin preview does not replay the entrance on every keystroke; takeovers remount per item (`key={item.id}`), so each one (and each turn of a shared rotation) plays it.
- **Adding a style** = a `.st-<id>` palette block in `takeover/css.js` (+ `.light` variant), an `ART.<id>` function in `art.js`, an entry in `design/announceStyles.js` (insets, `bb` side-graphic box, text-entrance personality) and in `shared/takeoverStyles.js` (id, group, label). `test/takeoverStyles.test.js` fails if any of the four is missing; then run the audit.

## Hebrew punctuation side, bilingual alignment, offline fonts (takeover type round, 2026-10-15)

- **Every text run gets its own direction.** The stage (and the admin preview root) is LTR, so a Hebrew run without its own `dir` shows "מזל טוב!" with the "!" on the RIGHT. Block elements with CSS `direction: rtl` were fine, but **inline spans ignore `direction` unless `unicode-bidi` is set** — the sub line / "where" / attribution pairs and kicker spans were wrong on the TV. Now `layouts.js` puts `dir="rtl|ltr"` on every run from `slotDir()` (`src/shared/bidi.js`: first strong letter, or any Hebrew in a Hebrew slot) and css.js isolates every `[dir]`. Inside an LTR line, Hebrew runs are wrapped as RTL spans with their closing `!?.`; inside an RTL line, Latin/time runs (`2:00 PM`, `9:30–10:00`) are wrapped LTR, otherwise they reorder to "PM 2:00". A bare time (`2:00`) orders itself. Hebrew typed into an English field (no Hebrew line) moves to the Hebrew slot (`takeoverModel.js`). The lively word-split skips text with `[dir]` children (inline-block words would lose the bidi order). Audit: `--len bidi` + the trailing-punctuation check.
- **Alignment rule** (README "Bilingual alignment"): start-aligned layouts put Hebrew and English on the same left edge whatever their direction (an RTL block with `text-align: start` drifts to the right edge — the tile's "הערב" did); centred layouts centre both. Only the two-column list / sicha header has English flush start, Hebrew flush end (stacked to the start edge in portrait).
- **Message & takeover fonts are presets, all bundled** (`settings.announceFonts`, `ANNOUNCE_FONT_PRESETS` in `src/shared/fontRoles.js`, imported in `src/screen/design/fonts.js`): editorial = Suez One (Hebrew display, single weight, display only) + Frank Ruhl Libre (Hebrew body, >= 500) + Playfair Display (English + numerals); modern = Rubik + Manrope; classic = Frank Ruhl Libre + Fraunces; screen = follow the global font roles (uploaded fonts such as FbMazal). **Never put a Google-Fonts-only family in a preset**: the old screen fetched Google Fonts at runtime and dropped to system fonts whenever the Wi-Fi blipped. Playfair / Fraunces default to old-style figures: the stage forces `lining-nums` (and `.num` adds tabular), and a Latin/time run inside a Hebrew display line uses the English display face, because Suez One's digits are old-style.
- **Fitting is balance-aware** (`fit.js settleLines`): after the binary search, a wrapped slot steps down (max 12%, never below its min) to avoid a last line under 40% of the longest, or to save a line when it has 3+. Gaps use the 8 px scale (`--sp1..--sp6` on `.stage`).

## Settings saves are PATCH, not PUT (2026-10-14)

Every panel used to PUT the whole settings object from its own stale copy, so the last save reverted other panels' keys. `updateSettings(patch)` now PATCHes only the keys passed; the server deep-merges (`src/shared/settingsMerge.js`). Don't spread the whole `settings` prop into a save, and add any new top-level setting to `SETTINGS_KEYS` or the server returns 400. Also: `SLIDE_FIELDS` in `api.js` is a whitelist, so a field the admin sends but isn't listed is silently dropped (this had blanked every new video slide).
